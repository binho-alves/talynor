## ADR-001 - React frontend

**Context:** Talynor requires a highly visual, responsive learning interface with interactive knowledge maps.

**Decision:** use React with TypeScript for a responsive SPA and standalone reusable UI components.

**Implications:** SPIKE-001 validated the initial graph experience. XYFlow / React Flow is adopted as the initial visualization library under ADR-007. ADR-010 uses local React state/custom hook for the scoped session flow, without selecting a broader state framework. Frontend testing tools and package manager remain open.

## ADR-002 - .NET 10 backend

**Context:** the backend needs an explicit application and domain boundary supporting learning workflows and persistence.

**Decision:** use .NET 10, ASP.NET Core, and C#, with EF Core and REST APIs documented using OpenAPI.

**Implications:** the authorized Phase 2 task created `Talynor.slnx` with Api, Application, Domain, Infrastructure, UnitTests, and IntegrationTests projects, `global.json`, and `Directory.Build.props`. Phase 2 is completed and approved. VS-001 explicitly authorizes a read-only demonstration endpoint, Application read models and reader interface, an Infrastructure in-memory implementation, and explicit mapping to independent HTTP contracts. Domain remains without artificial models. Phase 3.1 provides Identity persistence; 3.2A composes cookie/antiforgery infrastructure under ADR-008 without account/session endpoints. Product module boundaries and further implementation patterns remain open.

## ADR-003 - Modular monolith first

**Context:** the project is starting from zero and prioritizes simplicity and explicit responsibilities.

**Decision:** begin with a modular monolith.

**Implications:** keep business logic outside controllers and dependencies intentional. Module boundaries require later design; no microservice decomposition is approved.

## ADR-004 - SQLite first; PostgreSQL production target

**Context:** development and prototyping need an initial persistence approach, with a separate production target.

**Decision:** use SQLite initially and target PostgreSQL for production.

**Implications:** avoid unnecessary provider-specific behavior. Provider changes and migrations must be explicit, controlled, and validated. PostgreSQL infrastructure is not authorized at this stage and requires a later explicit request. Merely advancing roadmap phases does not authorize introducing it.

## ADR-005 - Knowledge graph without an initial graph database

**Context:** knowledge must support relationships beyond folders and trees; a node may open another map.

**Decision:** model knowledge as a graph domain concept while using the approved relational database strategy initially.

**Implications:** do not introduce a graph database. ADR-011 defines the initial relational model. Final relationship taxonomy and broader cross-map semantics remain open; the example relationships do not finalize them.

## ADR-006 - No premature distributed infrastructure

**Context:** infrastructure complexity must be justified by actual project needs.

**Decision:** do not introduce microservices, Redis, RabbitMQ, Kafka, Kubernetes, or Elasticsearch in the initial scope. Background workers require later justification.

**Implications:** address requirements within the approved modular monolith first. Any architectural departure requires explicit approval and an updated decision record.

## ADR-007 - Initial XYFlow graph visualization

**Context:** Talynor needs interactive knowledge maps with custom concepts, connections, and navigation between levels of detail. SPIKE-001 evaluated XYFlow / React Flow using React, TypeScript, and local mocks before the application skeleton. At adoption, the spike was completed and approved and Phase 2 had not started.

**Decision:** adopt XYFlow / React Flow as Talynor's initial graph visualization library. This is an accepted visualization-layer decision and may be reevaluated if concrete limitations emerge.

**Evidence:** SPIKE-001 validated custom nodes, edges, selection, dragging, zoom, pan, minimap, drill-down, TypeScript, basic responsiveness, and basic accessibility. Build and lint passed. These results establish initial suitability; the two five-node maps do not establish performance capacity for larger graphs or full accessibility compliance. Historical results and limitations remain in [the spike README](../src/frontend/talynor-web/README.md).

**Positive consequences:** reuse the validated interactions and custom React components; maintain typed visual data and callbacks; support incremental learning and implementation without an additional UI framework or application-level global state library. Drill-down remains application-controlled navigation, not a library-defined domain hierarchy.

**Isolation rule:** XYFlow is confined to the frontend visualization layer. Domain and application logic must not depend on XYFlow-specific types. API contracts and persistence must not expose or store XYFlow-specific Node/Edge structures as their domain or contract models. The spike's view types are presentation data, not domain entities; adopting the library does not decide relationship semantics or storage representation.

**VS-001 follow-through:** the explicitly authorized validation slice uses an independent HTTP contract, native fetch with cancellation, and a frontend adapter into XYFlow. Demonstration coordinates remain exclusively in the frontend. A configurable Vite development proxy supplies relative `/api` URLs without introducing backend CORS. No additional package manager, state library, automatic layout, persistence, or relationship semantics are selected.

**Risks and lock-in:** visual components, handles, event handling, Node/Edge view types, viewport behavior, and library CSS create integration costs. A future replacement would require adapting the visual layer and interactions; isolation reduces but does not eliminate that cost. Larger or denser graphs, richer nodes, and frequent updates may increase rendering cost. Real touchscreen behavior and full keyboard/screen-reader usability need further validation; narrow-screen overview text currently requires zoom. Dependency compatibility and ongoing maintenance remain considerations.

**Reevaluation criteria:** revisit adoption if representative product graphs remain unacceptably slow or memory-intensive after proportionate improvements; required touch or accessibility interactions cannot be achieved; an essential visualization requirement cannot be supported; library coupling obstructs domain evolution; or recurring compatibility, security, or maintenance problems undermine continued use. No artificial node-count limit is set.

**Still open:** automatic layout, final interaction design, relationship semantics beyond the initial relational foundation in ADR-011, and the official package manager. pnpm was used because it was available for the spike; npm, pnpm, or another option may be chosen later. This decision neither starts Phase 2 nor authorizes additional dependencies or infrastructure.

## ADR-008 - Incremental local Identity and persistence

**Status:** accepted; Identity persistence and session decisions are implemented and published in Phases 3.1 and 3.2. The approved workspace and frontend follow-through is published under ADR-009/010; Phase 3.5 validation and Phase 3 closure are completed.

**Context:** VS-001 is completed and published, with anonymous, read-only demonstration maps. Phase 3 needs durable account storage before identity/session HTTP workflows and personal-workspace ownership. The scoped Phase 3.1 task explicitly approves the strategy but authorizes only its persistence foundation.

**Decided:** use local ASP.NET Core Identity as the initial account system, EF Core with SQLite initially, browser cookies rather than JWT, and own HTTP endpoints rather than mapping the complete Identity endpoint set. One personal workspace per user was approved and is implemented under ADR-009; no second User/ApplicationUser entity is introduced without a concrete need. PostgreSQL remains the production target under ADR-004; infrastructure requires a later explicit request. No graph database is introduced.

**Implemented and published (3.1):** Infrastructure owns `TalynorDbContext`, based on `IdentityUserContext<IdentityUser>` without roles; SQLite provider and configurable local connection string; explicit `InitialIdentity` migration; design-time factory; local versioned `dotnet-ef`; tests of migrated schema, repeat application, cross-context persistence through the role-free Identity store, and API startup without database creation. Identity/EF types remain outside Domain and Application. No automatic startup migration, `EnsureCreated`, seed, or default credentials exist.

**Implemented and published (3.2A):** Phase 3.1 is completed and published. The API initially composed IdentityCore, existing EF stores, and SignInManager with only the `Identity.Application` cookie scheme; 3.2B.2A adds the technical auxiliary handler described below. `__Host-Talynor.Auth` is HttpOnly, Secure Always, SameSite Lax, Path `/`, without Domain, with an eight-hour ticket lifetime and no sliding expiration. Redirect events return 401/403 while preserving security-stamp validation; 3.2B.2B adds sanitized JSON bodies and no-store. Authorization has no global fallback policy. Native antiforgery uses `X-CSRF-TOKEN` and a separate `__Host-Talynor.Csrf` cookie (HttpOnly, Secure Always, SameSite Strict, Path `/`, no Domain). Anonymous `GET /api/auth/csrf` returns only the request token with no-store; a native MVC filter protects unsafe actions. Default local Data Protection remains in use. 3.2A added no login, seed, schema/migration/dependency/frontend change.

**Implemented and published (3.2B.1):** registration uses own `POST /api/auth/register`, without auto-login or an auth cookie. Email and username are identical after trimming external whitespace; Identity owns normalization and RequireUniqueEmail is true. The default username character whitelist is disabled to match the email contract, without provider-specific rules. HTTP limits are 256 UTF-16 units for trimmed email and 128 for password; password is never trimmed, case-changed, normalized, or truncated. RequiredLength is 15, RequiredUniqueChars is 1, and uppercase/lowercase/digit/non-alphanumeric requirements are false. Native Identity still rejects whitespace-only passwords. No blocklist or custom hashing is added, and this policy does not claim full security-standard compliance.

**Approved registration behavior:** Application's RegisterUser and IIdentityAccountService remain independent of Identity/HTTP/EF; Infrastructure uses UserManager and specific result mapping. The interface started as creation-only; 3.2B.2B adds only lookup by ID. The existing unique NormalizedUserName index is the concurrency guarantee while all writes maintain email=username. Only its exact SQLite UNIQUE failure becomes Duplicate; other database failures stay operational. No migration or unique NormalizedEmail index is introduced. Registration requires native CSRF and uses a native five-request/ten-minute fixed window per remote IP, QueueLimit zero, IPv4-mapped normalization, shared restricted missing-IP partition, and no forwarded-header trust. Responses: 201 without body/Location, 400 validation_failed or generic registration_failed, 409 already_authenticated, 400 csrf_invalid, 429 rate_limited, and sanitized 500 unexpected_error; no-store. A native per-action 8 KiB request limit is applied where supported by the HTTP server.

**Approved compatibility correction (3.2B.2A, completed, approved, and published):** a real SQLite/cookie/SignInManager diagnostic reproduced Identity 10.0.12's invalid-stamp rejection throwing InvalidOperationException because it explicitly signs out the absent `Identity.TwoFactorRememberMe` scheme. Register only that technical auxiliary cookie handler through the official `AddTwoFactorRememberMeCookie()` helper. Preserve the native `SecurityStampValidator<IdentityUser>`, application callback, 30-minute interval, and application-cookie policy; no custom validator or exception interception is used. Exactly Application and TwoFactorRememberMe are registered; authenticate, challenge, forbid, and sign-in remain Application defaults. External and TwoFactorUserId remain absent. No Talynor flow issues the auxiliary cookie, and no functional MFA is implemented. The regression requires native rejection, HTTP 401, cookie deletion, and rejection of original-ticket replay; valid-stamp renewal and registration without auto-login remain covered. Native auxiliary-cookie defaults are retained for this unused handler; any future functional use requires a separate security review. That slice introduced no schema, dependency, frontend, or session endpoint change.

**Implemented and published Session Flow (3.2B.2B):** own login/logout/me endpoints, Application LoginUser/GetCurrentUser and small ISessionService/ICurrentUser contracts. Scoped API adapters encapsulate HTTP/SignInManager and fail-closed NameIdentifier lookup; Infrastructure adds only account lookup by ID into AccountSummary. Native PasswordSignInAsync uses isPersistent=false and lockoutOnFailure=true, preserving the password and trimming only email. Existing authenticated login is 409 without switching; success is empty 204, and missing account/wrong password/lockout/not-allowed all return uniform 401 invalid_credentials. Operational failures remain sanitized 500, not invalid credentials. Login does not reapply creation policy.

**Session protections:** native lockout allows new users, with five failed attempts and five-minute lockout. Native login-only rate limiting permits ten requests per minute per remote IP, QueueLimit=0, IPv4-mapped normalization, shared missing-IP bucket, and no forwarded-header trust; registration quota remains separate and unchanged. Login/logout require native CSRF. Clients obtain a new CSRF request token after each identity change. Me/logout require Authorize, challenges/forbids remain 401/403 without redirects, and all auth responses are no-store. Me returns only ID and current email read from Identity; absent accounts cause local sign-out/401. The main cookie retains its policy and normal login has no Expires/Max-Age; the technical auxiliary cookie is never issued.

**Session boundaries:** multiple independent browser sessions are allowed; login does not invalidate prior sessions and logout deletes only the current browser cookie, without global ticket revocation or a session table. Login explicitly permits unconfirmed email; EmailConfirmed remains false, with no verification/reset workflow or provider. Account existence/lockout is not disclosed in errors, but timing remains distinguishable; compensatory hashing is explicitly deferred. Native stamp validation/renewal remains unchanged. Personal workspace/ownership is completed and published in 3.3 under ADR-009; frontend session integration is completed and published in 3.4 under ADR-010, with real-browser validation completed in 3.5. Recovery, verification, MFA, JWT, and other excluded account capabilities remain outside this slice.

**Consequences:** account storage can be verified independently of login and frontend behavior. The existing project-reference directions remain unchanged. The 3.1 schema includes Identity's user, claim, login, and token support tables but no roles, workspace, or knowledge-content tables; 3.3 adds only the personal-workspace table under ADR-009. The framework schema is not permission to expose additional account features. Phase 3 kept Knowledge Maps in-memory and the demonstration endpoint anonymous; ADR-011 adds separate private persistence.

**Risks and boundaries:** Identity's account schema introduces framework coupling in Infrastructure. SQLite and PostgreSQL have different provider/migration behavior; a future transition needs explicit review and validation. Local databases contain sensitive data and must remain untracked. Accounts remain unconfirmed and sessions do not imply production readiness. Generic duplicate/authentication errors do not eliminate enumeration through success/failure or timing. Blocklist, Unicode handling, password-hash cost, email verification, proxy/NAT behavior, and deployment security must be reviewed before public exposure. No private knowledge-data endpoint is introduced. Local Data Protection key persistence depends on the host profile; local browser TLS/cookie behavior was validated in 3.5, while deployment/key storage and comprehensive security still require review. Cookie/token/password values must never be logged.

## ADR-009 - Personal Workspace and Ownership

**Date/status:** 2026-10-13. Accepted by the scoped Phase 3.3 implementation request; implementation is completed, approved, and published. Phase 3.2 is completed, approved, and published.

**Context:** the local Identity/session foundation is available and a single personal workspace per user was approved in ADR-008. This slice needs authenticated ownership and persistent, concurrency-safe initialization without coupling account registration to workspace creation.

**Decision:** implement a minimal Domain PersonalWorkspace (Guid Id, string OwnerUserId, UTC CreatedAtUtc). Use Application GetOrCreatePersonalWorkspace and IPersonalWorkspaceStore; ownership is resolved only from ICurrentUser. Validate current account existence through the existing identity-independent account port. Creation time comes from TimeProvider. Resolve/create lazily through authorized `GET /api/workspace`, returning only id/createdAtUtc, always no-store. Register/login remain unchanged and do not initialize a workspace. Atlas terminology and its product relationship remain provisional.

**Persistence/concurrency:** EF Core/SQLite stores PersonalWorkspaces with required fields, an application-generated PK, and a UNIQUE owner index. Application first reads by owner; absent workspaces are inserted. The store recovers only the exact owner-index SQLite UNIQUE conflict, detaches the failed candidate, and rereads the existing workspace so concurrent first accesses return the same ID. No process-global lock, provider switch, generic repository, or new dependency is introduced. Other failures remain operational, sanitized HTTP 500.

**Account reference/lifecycle:** keep OwnerUserId as a logical reference without an Identity navigation, FK, or implicit cascade. This keeps Domain independent and avoids defining deletion behavior prematurely. Deleted accounts cannot pass the current-account check, but existing workspace rows are not deleted automatically. The check and workspace operation are not atomic with account deletion; lifecycle and orphan cleanup must be designed when delete-account is scoped.

**Consequences:** exactly one persisted workspace per owner; sequential access is idempotent and simultaneous inserts converge through database uniqueness. The endpoint accepts no client-supplied owner/workspace ID and does not expose owner ID, email, or claims. It can initialize an empty workspace through GET as explicitly approved. Tests use real migrated, temporary SQLite and deterministic insert synchronization, without sleeps or EF InMemory. AddPersonalWorkspace is an explicit migration; startup remains migration-free.

**Boundaries/risks:** Phase 3.3 kept Knowledge Maps anonymous, global and in-memory, without adding map ownership/persistence; ADR-011 introduces separate private persistence. No workspace CRUD/sharing/teams/roles, frontend auth, map CRUD, JWT, MFA, or PostgreSQL was introduced by 3.3. SQLite conflict classification is provider-specific and must be adapted/tested during an explicitly authorized PostgreSQL transition. Concurrency recovery is not a blanket retry for database busy/outage or other constraint failures. Authentication/deployment limitations documented in SECURITY.md remain applicable; no production-readiness claim is made.

## ADR-010 - Authenticated Frontend Session Flow

**Date/status:** 2026-10-13. Accepted by the scoped Phase 3.4 implementation request; implementation is completed, approved, and published. Phase 3.3 is completed, approved, and published; Phase 3.5 validation and Phase 3 closure are completed.

**Context:** the published backend provides login/logout/me, native antiforgery, and lazy personal workspace resolution. The existing React demo graph needs a session gate without changing its public map API or introducing new libraries.

**Decision:** use the browser-managed HttpOnly cookie, never an authentication token in JavaScript storage. Keep CSRF only in a private, in-memory session client. Use native fetch with relative same-origin URLs, credentials same-origin, no-store, explicit known error categories, and manual runtime validation. Bootstrap me before workspace; retain only the user's id/email and workspace id/createdAtUtc. Use React state, one custom hook, and conditional rendering without a router/state/form library or Context where no prop-drilling need exists.

**Transitions:** login obtains CSRF, sends credentials once, refreshes CSRF after 204, then reads me/workspace. A 409 rechecks the current account; it does not switch accounts or sign out. csrf_invalid renews once without replaying credentials. Logout obtains current CSRF, retries at most once after csrf_invalid, and treats 204/401 as ended locally. Known protected-read 401 clears local session; network/500/protocol errors are recoverable without assuming logout. New anonymous CSRF is deferred until login. Password remains transient form input, cleared after attempts/unmount, never persisted or logged.

**Consequences:** session and graph state remain separate. The existing Knowledge Maps are still anonymous, global demos, not personal workspace content. Conditional UI is not backend authorization. Request cancellation and identity guards handle StrictMode, retries, and unmounts; session changes discard graph state. Development requires trusted browser-to-Vite HTTPS using externally supplied certificate/key paths and verified Vite-to-API HTTPS, with no insecure proxy fallback.

**Risks/boundaries:** no cross-tab synchronization, polling, production hosting, token persistence, remember-me, frontend registration, workspace CRUD, or additional dependency. Another tab discovers changes only on a protected request/reload; an ambiguous POST/network failure can leave the browser session changed, requiring explicit session retry/reload. Local real-browser cookie/TLS, desktop/tablet/mobile layout, and accessibility smoke checks passed in Phase 3.5, including assisted Chrome Storage/Network inspection. Real touchscreen gestures and full accessibility remain unvalidated. Frontend test tooling and package manager remain open. Phase 3.5 completed Phase 3 closure without a production-readiness claim.

## ADR-011 - Persistent Knowledge Graph Foundation

**Date/status:** 2026-10-13. Accepted by the scoped Phase 4.1 request; completed, approved and published. Phase 3 is complete/published. Later backend authoring is separately authorized under ADR-012.

**Context:** the validated frontend still loads anonymous Software/C# demonstrations. PersonalWorkspace and validated current-user/account lookup are available. Durable private graph content needs its own relational model and read contract without changing those regressions or introducing a production/user seed.

**Decision:** add minimal Domain KnowledgeMap, KnowledgeNode and KnowledgeEdge with Guid identities. Maps belong to exactly one PersonalWorkspace; nodes and edges belong to one map. Map/node titles are required/trimmed with a 200 UTF-16-unit limit; optional descriptions have a 4000-unit limit. Finite double X/Y coordinates are application data, not XYFlow structures. Creation time is UTC from TimeProvider; map/node initial UpdatedAtUtc equals CreatedAtUtc. 4.2 resolves TimeProvider in Application, passes timestamps to Domain and advances UpdatedAtUtc without changing CreatedAtUtc. 4.1 did not add update API/UI.

**Membership/drill-down:** source/target nodes must belong to the edge's map; ChildMapId optionally refers to a map in the same workspace. No workspace field is duplicated in nodes/edges. No final relationship types, unique edge-pair rule, self-loop ban, cycle prohibition or automatic layout is selected. These graph semantics require later product decisions.

**Ownership/read boundary:** ICurrentUser → existing account check → server-resolved personal workspace → workspace-scoped map query. Reuse GetOrCreatePersonalWorkspace, including its approved lazy empty-workspace creation, without seeding content. A small IPersistedKnowledgeMapReader returns own Application projections; EF remains in Infrastructure. Private authorized GET /api/maps/{mapId:guid} returns id/title/description/nodes/edges, persisted node position and childMapId, never WorkspaceId/OwnerUserId or demo learning metrics. Anonymous/invalid/deleted-account requests get 401; foreign and missing maps get identical no-store 404. Operational failures, including pre-controller native stamp failures, get sanitized no-store 500. Cancellation propagates.

**Persistence/integrity:** EF Core/SQLite, no graph DB. Explicit workspace→map Restrict; map→nodes/edges Cascade; child→node Restrict; composite map/node→edge endpoint NoAction. An alternate (KnowledgeMapId, Id) node key prevents cross-map edges. SQLite triggers enforce child workspace equality on node insert/update and map-workspace changes. This protects concurrent/direct SQL writes without duplicating ownership columns or relying on an in-memory precheck. Trigger SQL stays in Infrastructure migrations and trigger metadata is recorded in the EF model. A finite-position CHECK protects storage as well. Required workspace/child/endpoint indexes are kept minimal; no speculative business index is added.

**Migration/transition:** AddPersistentKnowledgeGraph follows InitialIdentity then AddPersonalWorkspace, adding only graph tables, FKs, indexes, CHECK and equality triggers. Up/Down are explicit; startup does not migrate/create/seed. Preserve /api/knowledge-maps/software and /csharp as anonymous, global in-memory demonstrations. Phase 4.1 left the frontend consuming those routes; Phase 4.3 integrates /api/maps as the private persisted source. Test-only fixtures explicitly create graphs/workspaces; no development/production personal-map seed or default account is added.

**Consequences:** durable positions/drill-down and backend-enforced isolation are available without UI authoring or visual-library coupling. Independent HTTP projections keep Domain, Application, API and persistence free of XYFlow types. Existing cookie/CSRF/Identity behavior and dependencies stay unchanged. Relational constraints provide integrity for future writers without approving those writers now.

**Risks/future review:** triggers are SQLite-specific and must be preserved during table rebuilds and explicitly reimplemented/validated in a future PostgreSQL migration. In Phase 4.1, FK/trigger failures remained operational errors. Phase 4.2 translates only confirmed expected relation failures into controlled 400/409 responses under [ADR-012](#adr-012---knowledge-graph-authoring-api); unclassified failures remain operational errors and relations are never silently repaired. Referenced nodes/children/workspaces restrict deletion; future delete workflows must order removals/clear links explicitly, especially cycles. One read transaction gives a coherent snapshot but SQLite locking may serialize reads or contend with writes; there is no blanket busy retry or performance-capacity claim. Parallel reads are tested; Phase 4.1 did not define an editing-concurrency policy. ADR-012 records the Phase 4.2 baseline; advanced optimistic concurrency remains future work, without rowversion, ETag or If-Match in the current implementation. Account/workspace orphan lifecycle and non-atomic account deletion checks remain unresolved as in ADR-009. No public maps, sharing, study fields, CRUD/authoring UI, provider/dependency change or production-readiness claim is introduced. PostgreSQL infrastructure still requires explicit authorization.

## ADR-012 - Knowledge Graph Authoring API

**Date/status:** 2026-10-14. Accepted by the scoped Phase 4.2 request; completed, approved and published. 4.1 and Phase 4 are complete, approved and published. The explicitly authorized 4.3A discovery, 4.3 frontend integration (`f19c3d5`) and 4.4 authoring UX (`c427c6e`) follow-through are implemented, complete, approved and published.

**Context/decision:** durable private graph content needs nested authoring without frontend/schema changes. Use one Application use case per map/node create-update-delete and edge create-delete, a specific IKnowledgeMapStore, tracked scoped EF entities and atomic SaveChanges. Expose only nested /api/maps routes, deriving ownership from the validated current account/workspace. All unsafe endpoints require native CSRF and return no-store. Unknown DTO properties are rejected; creates return own 201 projections with map Location to its read, while PATCH/delete returns 204. Native 32 KiB bodies accommodate bounded text even with JSON escapes. No generic repository/transaction wrapper, new dependency or authoring limiter is introduced.

**PATCH/domain:** optional omitted/null fields keep state; clearDescription/clearChildMap flags explicitly clear nullable values. Clear-plus-value and empty PATCH are invalid. position:{x,y} requires both coordinates. Application supplies TimeProvider.GetUtcNow; Domain receives DateTimeOffset values and validates the complete candidate before mutation. Ownership, membership, ID and CreatedAtUtc cannot be patched. UpdatedAtUtc records the Application-supplied instant of an accepted map/node mutation operation and may change even when a valid PATCH repeats the current material values; no diff-before-update is required. It is not a concurrency token or a global commit ordering. CreatedAtUtc remains unchanged; edges remain immutable. Same-map self-loops/duplicate edges stay allowed; no relationship taxonomy, cycle ban or UNIQUE schema change is selected.

**Ownership/errors:** nested queries filter current workspace in SQL; missing/foreign target resources return identical 404. Missing/foreign child maps return 400 invalid_child_map; invalid/missing/cross-map edge endpoints 400 invalid_edge_nodes. Empty IDs/invalid fields are validation_failed. Application checks references before save and existing FKs/triggers remain defense-in-depth. Referenced child-map/node deletes get 409 map_in_use/node_in_use, never silent edge deletion. Only exact known relation failures with confirmed conditions are translated; busy/PK/other unknown failures remain sanitized 500. Concurrent zero-row UPDATE/DELETE is not found. Public responses/logs expose no provider details or private content.

**Concurrency/risks:** no rowversion/ETag/If-Match, history or audit framework. Same modified-column writes are last committed write wins; EF only writes changed properties, allowing disjoint changes to merge. UpdatedAtUtc is not a monotonic commit sequence. Constraint rechecks are not a blanket retry/locking policy. Account/workspace lifecycle and non-atomic account checks remain incomplete; native body limits require real-server verification. SQLite-specific classification/triggers must be adapted during an explicitly authorized PostgreSQL transition.

**Authorized discovery follow-through (4.3A, complete/approved/published):** extend the existing persisted reader with a workspace-scoped summary query and authenticated GET /api/maps. Use an own { "maps": [{ "id": "...", "title": "..." }] } API envelope, 200 with an empty maps array, database Title then Id ordering, and no-store. Ownership/account/error protections are reused. This read capability defines no root/default or automatic selection and adds no pagination/search, frontend, schema or dependency. The authorized frontend follow-through is described below.

**Phase 4.2 consequences:** backend authoring was added over the unchanged schema/migrations/snapshot/reader and existing session foundation; 4.3A subsequently extends only the reader's summary capability as described above. Demos remain anonymous/transitional; 4.2 left the frontend on demos, and the authorized 4.3 follow-through below replaces the authenticated experience. No frontend authoring, public/sharing/study capability, seed, provider/dependency change or production-readiness claim is introduced.

**Authorized frontend follow-through (4.3, complete/approved/published):** use `?map=<guid>` with native URLSearchParams/History API for the requested persisted-map view, F5 and visit-based Back/Forward, without a router dependency. No URL map means explicit discovery/choice; a valid deep link is an explicit request, not an automatic first-map policy. Current mounted navigation history is not a backend parent hierarchy; direct entry/reload offers the picker. GUID format checks do not authorize access: the existing server workspace boundary remains authoritative. Independent DTO validation/adapter keeps XYFlow visual only. At Phase 4.3 delivery, local drag reset on revisit/refetch and no authoring or browser-persistent state was added; Phase 4.4 adds the authoring follow-through below. **Decision/model:** KnowledgeNode has zero or many KnowledgeContents; each content belongs to exactly one node and cannot exist independently or be shared/moved between nodes/maps. Keep the validated URL without rewriting path/query/fragment. Localhost, private IPs and internal hosts are allowed. Foundation/backend originally introduced no content UI.

CHECK constraints reject unknown Type and inconsistent nullable Body/Url combinations; Domain remains responsible for nonblank values, URL policy and UTF-16 limits. EF max-length metadata alone is not SQLite enforcement. New content timestamps convert UTC DateTimeOffset to UTC DateTime storage and restore UTC DateTimeOffset when read; the instant/ticks are retained, original offset is intentionally not retained. This permits SQL CreatedAtUtc ascending then stored Id ascending ordering, including ties, without client sorting. Existing graph/Identity/workspace timestamp mappings are unchanged. No SortOrder or reordering UI/API is prepared.

**Ownership/read API:** reuse ICurrentUser → existing account check → server-resolved PersonalWorkspace, then SQL workspace/map/node/content filters. **Context:** the published product has private workspace-owned maps/nodes and Note/Link content. Phase 6 requires an agreed study-time workflow and history linked to relevant knowledge. No learning/content/node-completion measure is currently defined, and future Flashcards, Assessments and Progress/Analytics must not be folded into a generic activity container prematurely.

**Ownership/meaning:** KnowledgeNode 1 → N StudySession. Each session belongs to exactly one node and records private study effort; it has no KnowledgeContentId. Access follows ICurrentUser → existing account → server-resolved PersonalWorkspace → KnowledgeMap → KnowledgeNode → StudySession, reusing the approved account/lazy workspace resolution. No OwnerUserId, WorkspaceId or KnowledgeMapId is duplicated on the session, and no client ownership override is accepted. Node membership is immutable. Session completion means only that the temporal record ended, never node/content completion, mastery or proof of learning.

**Persisted model:**

| Field | Meaning |
| --- | --- |
| Id : Guid | Server-generated immutable identity. |
| KnowledgeNodeId : Guid | Required immutable node reference. |
| StartedAtUtc | Authoritative server UTC start instant. |
| EndedAtUtc nullable | Authoritative server UTC end instant, null while active and fixed on first completion. |

Duration is derived as EndedAtUtc minus StartedAtUtc, null until completion. Status is derived as active when EndedAtUtc is null, otherwise completed. No separate CreatedAtUtc, UpdatedAtUtc, persisted Duration/Status, Notes, Source, ClientStartedAt, LastHeartbeatAt, CompletedAt, SortOrder, RowVersion or generic JSON payload is included.

**Time/transition:** Application obtains server time through the existing TimeProvider direction and passes instants into Domain; Domain does not own a clock. Normalize DateTimeOffset to UTC for Domain/API and use explicit UTC DateTime storage conversion for SQLite, following the content timestamp precedent without changing existing mappings. Start is immediate and accepts no client time. Completion accepts no client end/duration. Zero duration is valid; an end before start is a conflict and must not mutate the record. A completed session cannot reopen or have its start/end edited retroactively. No counter is persisted each second, and the frontend timer is presentation only. Timezone conversion belongs to presentation, without a per-user timezone setting in this phase.

**Active invariant and SQLite:** at most one StudySession is active per PersonalWorkspace, across all its nodes, browsers and authentication sessions. Do not duplicate WorkspaceId merely to obtain a unique index. Start must use a specific atomic Infrastructure operation: acquire an appropriate SQLite write transaction (IMMEDIATE) before the query, validate node/ownership, query the workspace for an open session, return active_session_exists if present, otherwise insert and commit. Keep the transaction short; do not introduce a generic transactional wrapper. The official write path guarantees this invariant; there is no declarative constraint against arbitrary SQL INSERTs. Busy/timeouts are operational failures, not proof that an active session exists. A future PostgreSQL transition must explicitly revisit/test this strategy instead of assuming SQLite writer serialization transfers to another provider; PostgreSQL infrastructure remains unauthorized without a later explicit request.

**Interruption/recovery:** browser close, F5, navigation, logout, connection loss and device suspension do not complete the study period. It stays active until explicit completion or discard. Recovery offers Continue, Complete now or Discard. A forgotten session can remain open for hours/days: the user may complete it now or discard it, but cannot retroactively correct start/end. There is no heartbeat, timeout, beforeunload completion, worker, automatic completion or pause/resume.

**Retention and graph deletion:** StudySession is persistent personal history, not an immutable audit log. Completed sessions remain until confirmed explicit hard deletion; completed timestamps otherwise remain immutable. Discarding an active session hard-deletes it and permits a new start. There is no abandoned status, archive/restore or soft delete. The required node FK uses Restrict/NoAction, never cascade. Any active/completed session blocks node deletion with 409 node_in_use; a map containing a node with a session is blocked with 409 map_in_use. Users remove sessions consciously before their context; races must preserve this restriction without partial deletion. This history restriction is implemented and published through checkpoint 1. Existing edge/ChildMap blockers and ADR-013 KnowledgeContent cascades remain for otherwise permitted deletions. No orphan session or persisted node/map snapshot is introduced.

**HTTP contracts (approved design; backend published through checkpoint 2):**

| Method | Route | Behavior |
| --- | --- | --- |
| POST | /api/maps/{mapId}/nodes/{nodeId}/study-sessions | Start with server ID/time; 201 with DTO and Location to detail after persistence. |
| POST | /api/maps/{mapId}/nodes/{nodeId}/study-sessions/{sessionId}/complete | Complete with server time; 204, preserving the first end. Repeat on an owned already-completed record is 204 without mutation. |
| GET | /api/study-sessions/active | 200 with the current workspace's active session or null, minimal navigation context and serverTimeUtc in the envelope. |
| GET | /api/maps/{mapId}/nodes/{nodeId}/study-sessions | 200 with paginated completed node history. |
| GET | /api/maps/{mapId}/nodes/{nodeId}/study-sessions/{sessionId} | 200 with session detail. |
| DELETE | /api/maps/{mapId}/nodes/{nodeId}/study-sessions/{sessionId} | Explicit hard deletion, or active discard; 204. |

There is no generic PATCH. Start/complete have no business payload or client time fields. The own StudySession DTO contains id, knowledgeNodeId, startedAtUtc, endedAtUtc and derived durationSeconds (null while active). Active lookup may add mapId and current node title for navigation; this context and serverTimeUtc are response projections, not persisted snapshots. No owner/workspace field is exposed as a selection mechanism. A repeated complete targets the explicit sessionId and never completes a different current session. Start is not a general idempotent command: the active invariant prevents simultaneous open duplicates, but does not promise identity across arbitrary later retries. After an ambiguous response the client checks active/detail/history before another explicit attempt; no mutation replays automatically.

**History/persistence:** StudySessions table with Id PK and required KnowledgeNodeId FK Restrict/NoAction. CHECK (EndedAtUtc IS NULL OR EndedAtUtc >= StartedAtUtc). History index (KnowledgeNodeId, StartedAtUtc DESC, Id DESC); an auxiliary open-session index may be added if justified, without claiming unique-by-workspace on this normalized model. Completed history uses page-based pagination: page starts at 1 and defaults to 1 when omitted; pageSize defaults to 20 when omitted and has a maximum of 100. Ordering remains StartedAtUtc DESC then Id DESC; invalid/overflowing pagination is rejected. The envelope is sessions/page/pageSize/hasMore, without a mandatory COUNT. Offset pagination may repeat/shift entries when concurrent insertions/deletions occur; it is not a snapshot. No cursor, date filtering, global recent-history API or materialized counter is introduced by this initial design. Design acceptance alone did not create a migration or mapping; checkpoint 1 implemented both.

**Frontend (checkpoint 3 approved / published in 493d39a):** node details offer Start studying, including View mode. A global indicator in the authenticated shell shows the current study topic/elapsed time, Complete, return to node and explicit Discard. It lives above the node/map-specific mounted view, continues across node/map changes and Back/Forward, and recovers the active period from the backend after login/F5. Logout clears local state only. The timer derives display from server timestamps/time reference; an interval is not a source of truth or a write schedule. Completed node history shows start/end/duration, pagination and confirmed delete. Multi-tab awareness is refreshed on focus, explicit actions and refresh, without WebSockets, continuous polling, realtime or an instantaneous cross-tab guarantee. Concurrent starts conflict; concurrent completion preserves the first end. Keep existing session-private CSRF, native fetch/runtime DTO validation and stale/double-submit protection without introducing a framework or dependency.

**Security/errors:** all reads/writes require the existing authenticated session, account and server-derived ownership. Reads need no CSRF; writes use the existing native antiforgery mechanism. Private successes/errors are no-store. Missing/foreign/mismatched resources share generic 404 study_session_not_found. Existing authentication and sanitized operational/stamp failure behavior remains; do not turn failures into missing/empty data or expose private history in logs. Approved errors are 409 active_session_exists, 409 study_session_clock_conflict, 400 validation_failed, 400 csrf_invalid, existing 409 node_in_use/map_in_use and sanitized 500 unexpected_error. No session_already_completed code is needed for the idempotent completion result. Do not copy the graph/content 32 KiB configuration automatically for actions needing no business payload or claim real-server enforcement without verification. Cookie/HTTPS policies and the existing authentication system remain unchanged.

**Consequences/limits:** the minimal node context and server instants support study history without guessing time-based mastery or dependencies on future content/activity types. Explicit retention avoids silent history loss, at the cost of blocking graph deletion until sessions are removed. Forgotten sessions may overstate effort; the system does not detect attention or reconstruct offline stop times. SQLite start serialization can contend with other writes; offset history and multi-tab awareness are limited. The invariant depends on the official writer, not arbitrary external SQL. No ETag, rowversion, optimistic-concurrency framework, idempotency-key framework or snapshot taxonomy is selected. Provider transition and account/workspace orphan lifecycle retain their existing need for separate review.

**Outside the initial phase:** direct KnowledgeContent linkage; session notes; manual time entry/import or retroactive editing; pause/resume; heartbeat/timeout/automatic completion; Pomodoro; node/day/week totals, materialized counters, learning/content/node completion, percentages or mastery; goals/streaks/XP; notifications/calendar; Flashcards; Assessments; AI/recommendations; social/sharing; realtime/WebSockets; background workers; offline sync; advanced analytics; CSV/export; native mobile app; PostgreSQL infrastructure. The roadmap's completion tracking applies only where defined; no such learning-completion definition is approved here. Phases 7/8/9 retain their own design scope. Published implementation checkpoints and integrated closure evidence are recorded in [Development](DEVELOPMENT.md#phase-6---approved-design-and-planned-checkpoints); design acceptance alone did not authorize implementation.

**Context:** Phase 5 delivers private Note/Link KnowledgeContent under a node. Phase 6 records explicit study periods and intentionally does not define learning mastery. Flashcards need editable learning content, repeatable review and durable progress without coupling content to an algorithm or silently treating review as a StudySession.

**Decision — entity and ownership:** choose option B: Flashcard is its own Domain entity, directly related to exactly one KnowledgeNode. It is not a KnowledgeContent subtype, is not a hybrid, does not require Note/Link, and has no KnowledgeContent reference in the initial phase. This keeps prompt/answer validation and lifecycle specific, lets card workflows evolve independently of Phase 5's stable Note/Link contract, and avoids an extra object just to create a card. Ownership is derived only through ICurrentUser → existing account → PersonalWorkspace → KnowledgeMap → KnowledgeNode → Flashcard. Persist no OwnerUserId, WorkspaceId or MapId. Node relationship permits direct node creation and ownership, with optional cross-reference deferred rather than implicitly modeled.

**Card contract:** Flashcard has server-generated Id (Guid), immutable KnowledgeNodeId (Guid), Front, Back, ContentRevision (positive .NET Int32 / JSON integer), immutable CreatedAtUtc, and server-owned UpdatedAtUtc. Front is required plain text, maximum 2,000 .NET UTF-16 code units; Back is required plain text, maximum 4,000. Reject empty/whitespace-only values, but preserve submitted text exactly, including leading/trailing whitespace and newlines. Validation does not trim or normalize the persisted text. Compare final text with persisted text using ordinal equality, without case, Unicode or newline normalization. React renders escaped text only; no Markdown/HTML. No title, hint, tags, media, source, explanation, card subtype or generic metadata is approved initially.

**ContentRevision and edit policy:** ContentRevision starts at 1 in Checkpoint 1. A textual change to Front or Back increments it once and advances UpdatedAtUtc using server time; CreatedAtUtc never changes. Empty and material no-op PATCH are 400 validation_failed, following the Phase 5 content precedent: no save, revision increment, timestamp change or review-state reset occurs. Overflow must fail without mutation or wrapping. This is a narrow review-versus-edit guard, not general rowversion/ETag concurrency control. From Checkpoint 2, a material edit also deletes the optional FlashcardReviewState row atomically with the content/revision update. The new revision projects reviewCount 0, correctCount 0 and lastReviewedAtUtc null and returns to the never-reviewed group. Historical events keep their original ContentRevision and are not deleted by an edit. The assessed content changed, so old-version progress must not determine the new revision's rotation priority. The official SQLite edit operation reads the current card inside a short IMMEDIATE transaction and commits the text/revision and reset together, serialized with review writes; this also prevents concurrent edits from losing a revision increment.

**Request bounds:** Phase 7 write actions use a 64 KiB (65,536-byte) native request-body cap, replacing the proposed 32 KiB for these actions only. At most 6,000 Front/Back UTF-16 units can occupy 36,000 bytes when every unit uses a six-byte JSON Unicode escape; property names, punctuation and the small fixed contracts fit with substantial headroom. Every allowed Front/Back value therefore fits even with maximal string escaping. Excessive wire padding/whitespace still counts toward the body cap; the cap is independent protection, not a replacement for field validation. Unknown request members, invalid/null values and client identities/ownership/timestamps are rejected. Existing Phase 4/5 limits are unchanged. Real-server enforcement must be verified during implementation; TestServer metadata alone is insufficient. No dependency is introduced.

**Decision — learning state and history:** separate learning state from card content. Optional FlashcardReviewState has FlashcardId as PK/FK, ReviewCount, CorrectCount and LastReviewedAtUtc; create it on the first accepted review of the current content revision. The present row describes that revision only: ReviewCount >= 1, 0 <= CorrectCount <= ReviewCount and non-null LastReviewedAtUtc. Absent state projects 0, 0, null. These materialized values are derivable from current-revision events, but avoid repeated COUNT/aggregation for progress and rotation reads. Persist each accepted answer as immutable FlashcardReview with ReviewId (client-generated nonempty Guid, PK), FlashcardId (Guid, FK), ContentRevision (positive Int32 actually answered), Result (Domain Correct/Incorrect, stable stored/JSON strings `correct` / `incorrect`) and server-generated ReviewedAtUtc. Event insertion and state creation/update commit atomically, with no event-only or state-only success. Historical events survive content edits, not card deletion. No history-list or analytics API, DueAtUtc, interval, ease, scheduler repetition/lapse counters or last-result duplicate is included. Binary history cannot reconstruct a richer rating that was never collected.

**Decision — continuous study without scheduling:** Correct/Incorrect is self-reported recall, not mastery. No spaced-repetition scheduler, FSRS or SM-2 is selected. All cards remain eligible. A node-scoped LEFT JOIN to optional state selects one item: first cards without state ordered CreatedAtUtc ASC, Id ASC; only then reviewed cards ordered LastReviewedAtUtc ASC, CreatedAtUtc ASC, Id ASC. Never-reviewed cards intentionally take priority while any remain, including new or materially edited cards. After each answer, next recalculates from persisted state; deleted cards are excluded. Empty nodes return 200 with item null; when all cards are reviewed, next still returns an item. With one card it can immediately reappear. There is no deck-complete state, persistent queue, backend study run, client-side round tracking, batch limit or cursor; the user leaves whenever desired. Refresh/navigation resumes the current rotation, not an exact run position. This deterministic rotation is not spaced repetition and does not promise retention optimization.

**StudySession relationship:** reviewing does not require or create a Phase 6 StudySession and has no FK to one. FlashcardReview records answer events; StudySession records explicit elapsed study periods. Users may use both independently. Any future integration is a separate decision.

**API direction — authoring:** all routes below use the base `/api/maps/{mapId}/nodes/{nodeId}/flashcards`; all IDs are Guid, and all operations enforce the authenticated workspace/map/node/card ownership chain in SQL. Reads/errors are no-store without CSRF; writes/errors are no-store with existing native CSRF. Own DTOs expose no Domain/EF types or ownership selectors. FlashcardDto is `{ id, knowledgeNodeId, front, back, contentRevision, createdAtUtc, updatedAtUtc }`. GET collection retains the CP1 contract `{ flashcards: [FlashcardDto], page, pageSize, hasMore }`, without ReviewState. Authoring detail also remains FlashcardDto; study-next provides the separate study projection with current reviewState, and review PUT/GET provide review plus currentReviewState. A future authoring review-state wrapper would require separate scoped authorization and is outside Checkpoint 2. page defaults to 1 (minimum 1); pageSize defaults to 20 and accepts 1..100, rejecting larger/invalid/overflowing inputs with 400 validation_failed rather than clamping. Order CreatedAtUtc ASC, Id ASC; use a bounded pageSize+1 SQL query to derive hasMore without mandatory COUNT. Parent validation and page projection share a read snapshot; pages are not a snapshot across requests and may shift under concurrent changes. Empty owned nodes return an empty flashcards array. GET detail returns FlashcardDto. POST collection returns 201 with FlashcardDto and detail Location; successful PATCH detail and DELETE detail return 204. PATCH accepts only supplied non-null Front/Back, keeps omissions and rejects unknown/blank/empty/no-op patches as above.

**API direction — study and reveal:** GET `/api/maps/{mapId}/nodes/{nodeId}/flashcards/study/next` returns 200 with `{ item: null }` or `{ item: { id, front, contentRevision, reviewState: { contentRevision, reviewCount, correctCount, lastReviewedAtUtc } } }`. It never returns Back. Only explicit Reveal initiates GET `/api/maps/{mapId}/nodes/{nodeId}/flashcards/{flashcardId}/study/reveal?contentRevision=R`. The observed positive Int32 query value is required exactly once. A scoped read validates the current revision and returns 200 `{ flashcardId, back, contentRevision }` only if it still equals R; mismatch returns 409 flashcard_changed without Back, and a missing/foreign/mismatched card returns generic 404 flashcard_not_found. Invalid revision input is 400 validation_failed. A read snapshot/one scoped projection prevents mixing a question revision with a different answer. On flashcard_changed, discard the stale item/answer, tell the user the card changed, and fetch next; a later edit between reveal and submission is checked again by the review writer. No prefetch, DOM hiding alone or cached authoring Back substitutes for explicit study reveal. Authoring reads intentionally include Back for the owner; this reveal boundary supports study UX, not secrecy against an owner who can read/edit the card.

**API direction — review and lookup:** PUT `/api/maps/{mapId}/nodes/{nodeId}/flashcards/{flashcardId}/reviews/{reviewId}` accepts only `{ result: "correct" | "incorrect", contentRevision }`. First commit and same-payload replay return 200 after commit with `{ review: { reviewId, flashcardId, contentRevision, result, reviewedAtUtc }, currentReviewState: { contentRevision, reviewCount, correctCount, lastReviewedAtUtc } }`. GET on that same review route is authenticated/scoped/no-store without CSRF and returns the same envelope, or generic 404 flashcard_not_found for an absent/foreign/mismatched review. Never look up or expose ReviewId outside the ownership chain. The immutable review identifies the accepted payload and original server time. currentReviewState is the card's current revision/progress read consistently with the event, not a stored historical snapshot of the original write: later reviews may advance it and edits may reset it. No extra event snapshot columns are introduced. An old event remains confirmable after an edit, without reviving its old progress.

**Idempotency and concurrency:** after acquiring a synchronous submit lock and before its first request, the client generates one nonempty Guid ReviewId when the learner presses Correct/Incorrect, not on reveal. Keep it and the exact card/revision/result in the pending mutation until resolved; a new deliberate answer gets a new ID. Semantic equality is exactly FlashcardId + ContentRevision + Result. Repeating the same ReviewId and payload returns the original event/ReviewedAtUtc, with no event insert, count increment or LastReviewedAtUtc update. Reuse with any different semantic value returns 409 review_id_conflict, with no foreign event details.

The official review writer begins a short SQLite BEGIN IMMEDIATE before ownership/operation reads, on the same connection enlisted with EF. Resolve current ownership, check/replay an existing ReviewId before comparing the current card revision, otherwise verify revision, insert event and create/update current state, then commit atomically. Replay of a previously committed old-revision event after an edit confirms that event without recreating/resetting progress; only a new stale operation gets flashcard_changed. ReviewId PK is the final duplicate guard. Same-ID/same-payload concurrent requests converge on one event and one state transition; both see that result unless other operations subsequently change current state. Same-ID/different-payload conflicts. Different ReviewIds serialize their read/update and count as separate intentional answers, preventing lost updates even across tabs. Text edits/reset use the same SQLite writer serialization; review/delete races preserve FK/cascade and never resurrect a card. Native lock waits may be synchronous with limited immediate cancellation; busy/timeouts remain sanitized operational failures, without automatic retries. No generic framework, global lock, realtime coordination, arbitrary-writer or PostgreSQL guarantee is introduced; provider transition requires separate review.

**Ambiguous write recovery:** query the same scoped ReviewId. A 200 whose review fields match the saved card/revision/result confirms the operation; use currentReviewState only for its reported current revision, then refetch next. A 200 with different semantic data is a conflict and must not be treated as confirmation. A 404 does not prove a delayed request cannot still commit; only an explicit retry with the same ID and original payload is permitted, preserving idempotency. Lookup failure keeps the unresolved operation recoverable. Never automatically replay, change its payload or generate a replacement ID to resolve ambiguity. Navigation/logout discards local presentation without proving rollback; later reads recover persisted state.

**Persistence/deletion:** explicitly select migrations `AddFlashcards` then `AddFlashcardReviews`; startup never migrates/creates/seeds. Keep DateTimeOffset UTC in Domain/API and use explicit UTC DateTime SQLite conversion. Flashcards has a required KnowledgeNode FK Cascade, positive ContentRevision CHECK and index `(KnowledgeNodeId, CreatedAtUtc, Id)`. ReviewState uses FlashcardId PK/FK Cascade and count/last-time checks; deleting this optional row resets the current revision only, not its events. Reviews uses ReviewId PK, FlashcardId FK Cascade, positive ContentRevision CHECK (not an FK to the card's changing revision), stable result CHECK and `(FlashcardId, ReviewedAtUtc DESC, ReviewId DESC)` index for card-scoped events/cascade. ReviewState adds `(LastReviewedAtUtc, FlashcardId)` for rotation. No duplicate owner/workspace/map columns, PostgreSQL infrastructure, graph database or new provider is selected.

Explicit card deletion is hard delete and cascades review state/history; the UI confirms irreversible deletion. Deleting an otherwise deletable node cascades its cards and review data, and cards alone do not block node/map deletion. Existing edge, ChildMap and StudySession blockers remain authoritative; a StudySession still blocks node/map deletion. This differs intentionally from Phase 6's retained study history: card text and per-card practice history share a user-controlled deletion lifecycle, while elapsed StudySession history has a separate retention rule.

**Security and errors:** all operations require the current authenticated account and server-derived workspace ownership; never accept client ownership selectors. Unknown/invalid request fields are rejected, inputs are bounded, private successes/errors are no-store, reads require no CSRF and writes use native antiforgery. Strict JSON follows existing patterns, without claiming dedicated duplicate-property rejection. Never log Front/Back/review content, credentials or tokens. Missing/foreign/mismatched card paths and absent scoped reviews share 404 flashcard_not_found. Use 400 validation_failed/csrf_invalid, 409 flashcard_changed/review_id_conflict, existing sanitized 401 and 500 unexpected_error. No client review timestamp or study Back delivery before explicit reveal.

**Frontend direction:** add a Flashcards section in NodeDetails, preserving Note/Link UX. Edit map provides paginated list/create/edit/confirmed delete; View mode offers Study without preloading the authoring list/Back. Refetch authoring page one after writes. Continuous study has loading/no-cards/prompt/revealed/submitting/next/error-retry states and an explicit way to leave, never completed-deck UI or a persisted run. Back is fetched only by explicit Reveal and is absent from the DOM/accessibility tree until then. Native labeled buttons, focus behavior and touch-friendly single-column controls support keyboard/mobile use without hover or required shortcuts. Use existing runtime validators/native fetch/scoped hook-coordinator, with AbortController/request identity for list, next, reveal and review lookup; navigation must not accept an old response. Lock synchronously before generating ReviewId. On flashcard_changed discard stale prompt/answer and fetch next; on flashcard_not_found refetch next without resurrection; require another deliberate answer. Preserve same-ID ambiguous-write recovery without automatic mutation replay. Logout clears local UI only. No router/state/test library or dependency is added.

**Alternatives considered:** a KnowledgeContent subtype or hybrid was rejected in favor of direct node ownership and a separate card lifecycle; keeping old progress after a text edit was rejected because it would prioritize new content using old answers. Sending Back with next and hiding it only in the DOM was rejected in favor of revision-matched explicit reveal. Deriving all counts from events on every read was rejected in favor of a small atomically maintained current-revision state. SM-2/FSRS, richer ratings, fixed runs/snapshot queues and generic concurrency/idempotency frameworks remain deferred rather than partially implemented.

**Consequences and limitations:** the independent entity keeps KnowledgeContent stable. Separate state/events keep progress out of card text; current counters describe only the latest revision, while historical events retain older revisions. Explicit reveal costs one extra read and does not prevent an owner from inspecting their authoring content. No scheduler promises due dates, retention optimization or mastery; Correct/Incorrect are self-report. Hard deletion erases review history and therefore removes it from any future analytics. SQLite immediate locking is local/provider-specific; arbitrary external writers and future PostgreSQL semantics need new design. ContentRevision protects only review-versus-edit staleness, not lost-update-free generic CRUD. Rotation is not a queue snapshot; offset authoring pages can shift/repeat/omit entries under concurrent changes. Native lock waits, real-server body-limit enforcement, full accessibility and physical touchscreen behavior need scoped implementation verification; no production-readiness claim follows.

**Future compatibility:** a later scheduler can consume persisted review instants/events and basic counters, but binary results cannot recreate Hard/Easy distinctions; adopting FSRS or another scheduler will require an explicit mapping/reinitialization policy and likely new state fields. Additional card types can be introduced with reviewed schema/domain evolution rather than a generic payload. Sharing/public ownership, imports, AI provenance and analytics need their own access, lifecycle and data-contract decisions. The selected model leaves these paths open without implementing or promising them.

**Implementation follow-through — checkpoints (each needs explicit scoped authorization):** (1) card Domain including ContentRevision from the start, `AddFlashcards`, paginated scoped read/CRUD, atomic revision updates, hard delete/cascade and backend tests, without review tables; (2) ReviewState/events with ContentRevision, `AddFlashcardReviews`, edit/reset integration, deterministic next, revision-matched reveal, PUT review/GET lookup, same-connection BEGIN IMMEDIATE atomicity/idempotency/concurrency and tests; (3) frontend NodeDetails authoring and continuous study/reveal/result/reconciliation with stale-response guards, runtime checks and responsive/accessibility/browser validation; (4) integrated backend/frontend/security/accessibility/migration regression and formal closure, without new features. The design baseline alone started no implementation. Checkpoint 1 is published in f375141, Checkpoint 2 in 8af676d and Checkpoint 3 in f58d0fe. Checkpoint 4 integrated validation completed on 2026-10-21; Phase 7 is complete for the approved scope. Phase 7 closure was formally approved and published in bc7a4b6.

**Outside Phase 7 initial scope:** KnowledgeContent references; additional card types; hints/tags/media/source/explanation; Markdown/HTML; manual sort; random or snapshot queues; spaced repetition/FSRS/SM-2; learning mastery/aggregates; StudySession coupling; shared/public decks/marketplace; Anki import; image occlusion/cloze; AI generation; collaboration/realtime; reminders/notifications; advanced analytics; achievements/leaderboards; FSRS optimization/training; offline/mobile/native app; PostgreSQL infrastructure; and new frameworks/dependencies.

## ADR-016 - Node-owned quizzes, revision-scoped grading and immutable attempts

**Date/status:** 2026-10-21. Accepted by the explicit Phase 8 Checkpoint 0 formalization request; CP0 is Published in 39ff3aa and CP1 in 4b6dec0. Phase 7 and its closure are complete, approved and published in bc7a4b6. Phase 8 is In Progress; CP2 Submission, grading and history backend is Implemented / under review, not published. CP3-CP4 are Not started. CP0 introduced only design; backend implementation now includes the CP1/CP2 follow-through below.

**CP1 follow-through (2026-10-21):** implements Quiz/QuizQuestion/QuizOption, AddQuizzes and six nested definition list/detail/create/full PUT/delete/take routes. Title uses outer trim; literal question/option text and ordinal trimmed duplicate checking follow this ADR. A complete candidate validates before mutation; expectedRevision is checked inside the same-connection SQLite BEGIN IMMEDIATE writer. Replacement regenerates child IDs; explicit old-question SQL deletion avoids unique-position conflicts, followed by one SaveChanges in that transaction. No-op/invalid/stale/overflow saves nothing; errors roll back deletes/new children and detach candidates. List uses parent/page snapshot and pageSize+1; authoring/take each use one ordered AsSingleQuery projection. Separate take DTOs and SQL select no key. Native antiforgery/strict own JSON/no-store, body-free DELETE and bounded 256 KiB POST/PUT are scoped to CP1. No attempt type/table, grading/submission/history, frontend, new dependency or startup migration is introduced. This paragraph records the CP1 boundary; CP2 implementation and current evidence follow below and in Development.

**CP2 follow-through (2026-10-21):** implements immutable QuizAttempt/answer/all-option snapshots, AddQuizAttempts, complete server grading and three submission/history/lookup routes. Official same-connection BEGIN IMMEDIATE serializes with edits/deletes; ownership precedes existing AttemptId comparison, which precedes current revision validation. Matching replay ignores answer order and returns the original result/time after edits without regrading; different payloads conflict. New writes save counts/snapshots once and roll back/detach on failure. History/detail use scoped historical projections; current child IDs are not history FKs. Native/bounded 16 KiB submission enforcement reuses the parameterized Quiz filter without changing authoring's 256 KiB cap. Independent SQLite connections/gates, rollback, migration, IDOR and Kestrel tests supply backend evidence; frontend reconciliation/CP3 remains planned.

**Context:** Phase 8 Assessments supports simple quizzes to check understanding, creation/answering, recorded results and agreed scoring linked to knowledge. Private maps/nodes, Note/Link content, Study Sessions and Flashcards already exist. QuizAttempt records performance on one definition, not mastery, proficiency or KnowledgeNode completion. Phase 9 may consume results later; Phase 8 defines no aggregate progress measure.

**Decision — ownership and lifecycle:** Quiz is a separate node-owned Domain feature, not a KnowledgeContent subtype and not dependent on Note/Link or Flashcards. Ownership is ICurrentUser -> existing account -> server-resolved PersonalWorkspace -> map -> node -> quiz, with SQL-scoped nested access and no duplicate OwnerUserId, WorkspaceId or MapId. Reuse approved lazy workspace resolution without creating a quiz or attempt through GET. The initial format is single choice, exactly one correct option per question, complete submission and automatic server-side grading. No teacher/student model or formal examination guarantee exists.

There is no persisted active attempt or draft. Before submission, answers live only in frontend memory and may be discarded on leave, context change, logout or F5. There is no start-attempt endpoint, autosave, resume, pause, timer, timeout or beforeunload persistence. An accepted attempt is immutable. Answering does not require, start or end a StudySession and has no StudySessionId; future integration needs its own decision.

**Domain baseline:** IDs are nonempty Guids. Application obtains server UTC time through TimeProvider and passes instants to Domain; Domain owns no clock, HTTP, EF or XYFlow types.

| Concept | Persisted values / responsibility |
| --- | --- |
| Quiz | Server Id, immutable KnowledgeNodeId, Title, positive Int32 ContentRevision initially 1, immutable CreatedAtUtc and server UpdatedAtUtc. |
| QuizQuestion | Server Id, QuizId, Text and Position (1..10 within the quiz). |
| QuizOption | Server Id, QuestionId, Text, Position (1..4 within the question) and internal IsCorrect. |
| QuizAttempt | Client AttemptId, QuizId, answered ContentRevision, server SubmittedAtUtc, QuestionCount, CorrectCount and QuizTitleSnapshot. |
| QuizAttemptAnswer | AttemptId, historical QuestionId, Position, QuestionTextSnapshot, SelectedOptionId and CorrectOptionId. Its per-question result is derived by ID equality. |
| QuizAttemptAnswerOption | AttemptId, historical QuestionId, historical OptionId, Position and TextSnapshot for each option actually presented. |

**Bounds and text:** Title is required, trimmed at its outer whitespace, nonblank and at most 200 UTF-16 code units after trimming. A quiz has 1..10 questions; Text is required/non-whitespace and at most 1000 units. Each question has 2..4 options, each required/non-whitespace and at most 500 units. Question/option text is persisted literally, without trimming, case folding or Unicode/newline normalization. Duplicate option detection compares outer-trimmed text with ordinal equality within one question, rejecting equal text and surrounding-whitespace-only variants without rewriting stored text; it does not infer synonyms. Domain whitespace rules are authoritative and frontend validation must mirror them, including Unicode edge cases rather than assuming every JavaScript/.NET whitespace helper is identical. JavaScript string.length and .NET string.Length count UTF-16 units. Array order is explicit, not randomized; persisted positions are one-based, while correctOptionIndex in authoring is zero-based. Domain/writer validates exactly one correct option and a complete valid candidate before persistence.

**Definition replacement/revision:** POST creates a complete valid definition and server IDs. PUT replaces the entire definition and requires expectedRevision; there is no granular question/option PATCH. Ownership/node/Id/CreatedAtUtc cannot change. Compare the normalized title, literal question/option text, sequence and correct choices with the current definition. Any material difference increments ContentRevision once and updates server UpdatedAtUtc; question/option IDs may be regenerated on replacement. Check expectedRevision before applying an edit: stale is 409 quiz_changed. A material no-op is 400 validation_failed without save, timestamp/revision change or partial child replacement. Checked revision overflow fails without mutation/wrapping and uses sanitized unexpected_error, as in the Flashcard boundary. The frontend never predicts authoritative revision. Editing preserves all accepted attempts; there is no current review state to reset.

**Historical snapshots:** QuizAttempt references the still-owned Quiz by FK, preserving its title at acceptance and the answered revision. Each answer copies the question text/order and all presented option IDs/texts/order, plus selected/correct option IDs. This preserves the actual choices, not just the selected and correct text. The small relational child QuizAttemptAnswerOptions is necessary for the bounded 2..4 presented options and avoids a generic JSON payload or four parallel nullable option columns. QuestionId/OptionId/SelectedOptionId/CorrectOptionId in history are historical identifiers, never FKs to current QuizQuestions/QuizOptions. Selected/correct IDs must identify copied options, enforced by the Domain/official writer without a circular FK. Historical rows have their own parent FKs described below. Do not copy owner/workspace/map, current node title, a second entire quiz definition, redundant per-answer IsCorrect or persisted percentage. Results always project these immutable snapshots, never current question/option text. Revision and original result/time remain meaningful after editing, including replacement/removal of current children.

**Scoring:** each question is worth one point, without weights, partial credit, penalties, pass/fail threshold or mastery. The server accepts exactly one answer for every question of the submitted current revision, verifies each selected option belongs to that question, and rejects missing/extra/duplicate questions or invalid options before saving. Store QuestionCount (1..10) and CorrectCount (0..QuestionCount) with all answers atomically; these values must agree with the immutable answer snapshots. Derive accuracyPercentage using decimal arithmetic: Round(100m * CorrectCount / QuestionCount, 2, MidpointRounding.AwayFromZero). The API exposes the resulting JSON number and the UI formats exactly two decimal places (2/3 -> 66.67, shown as 66,67% in pt-BR). Do not persist percentage, accept client scores/timestamps or grade again when reading/replaying a result.

**Persistence baseline — definitions and attempts implemented in CP1/CP2:** EF Core/SQLite; DateTimeOffset UTC in Domain/API, with the established explicit UTC DateTime storage conversion. Nonempty IDs and text/cardinality/complete-snapshot rules are Domain/writer responsibilities; SQLite max-length metadata alone does not enforce UTF-16 bounds.

| Table (CP1 definitions / CP2 attempts) | Keys, indexes, practical constraints and parent behavior |
| --- | --- |
| Quizzes | Id PK; KnowledgeNodeId FK Cascade; ContentRevision > 0 CHECK; (KnowledgeNodeId, CreatedAtUtc, Id) index. |
| QuizQuestions | Id PK; QuizId FK Cascade; Position 1..10 CHECK; UNIQUE (QuizId, Position). |
| QuizOptions | Id PK; QuestionId FK Cascade; Position 1..4 and IsCorrect in (0,1) CHECKs; UNIQUE (QuestionId, Position); UNIQUE QuestionId WHERE IsCorrect = 1. |
| QuizAttempts | AttemptId PK; QuizId FK Cascade; ContentRevision > 0, QuestionCount 1..10 and 0 <= CorrectCount <= QuestionCount CHECKs; (QuizId, SubmittedAtUtc DESC, AttemptId DESC) index. |
| QuizAttemptAnswers | (AttemptId, QuestionId) PK; AttemptId FK Cascade; Position 1..10 CHECK; UNIQUE (AttemptId, Position); snapshot text and selected/correct historical IDs. |
| QuizAttemptAnswerOptions | (AttemptId, QuestionId, OptionId) PK; composite (AttemptId, QuestionId) FK to QuizAttemptAnswers Cascade; Position 1..4 CHECK; UNIQUE (AttemptId, QuestionId, Position); snapshot text. |

The filtered option index guarantees at most one current correct option, not at least one; Domain/official writers guarantee exactly one, minimum child counts and result/snapshot consistency. Do not claim that schema alone enforces every invariant against arbitrary SQL. Attempt ContentRevision is not an FK to the changing Quiz revision. CP1 implements AddQuizzes for the first three tables; CP2 implements AddQuizAttempts for attempts and both snapshot tables. CP0 created no migration; CP1 added only AddQuizzes and CP2 only AddQuizAttempts. Up/Down/reapply must preserve earlier data, FKs and graph triggers. Startup never migrates/creates/seeds; PostgreSQL infrastructure still requires an explicit request and a new provider/concurrency review.

**Deletion:** confirmed quiz deletion is hard delete, cascading current questions/options and attempts/answer/option snapshots. History is personal data, not a permanent audit log: edits retain it, deletion intentionally removes it. Existing edge/ChildMap/StudySession node/map blockers remain; quiz/history creates no new blocker. An otherwise permitted node/map deletion cascades quiz/history, while a blocked deletion leaves all data intact without partial cascade. No orphan snapshot, archive/restore, independent historical-attempt delete endpoint or account-cleanup policy is introduced. Replaying an ID after its quiz was deleted returns not-found and cannot resurrect it.

**API baseline — six CP1 definition/authoring/take routes and three CP2 attempt routes implemented:** base `/api/maps/{mapId}/nodes/{nodeId}/quizzes`; all IDs are Guid and ownership is server-derived. All operations/errors require the existing authenticated account and no-store. GETs require no CSRF; every unsafe operation requires existing native antiforgery. Own API DTOs expose no persistence/library types, ownership selectors or client timestamps.

| Method | Relative route | Contract / successful result |
| --- | --- | --- |
| GET | collection | {quizzes:[QuizSummary],page,pageSize,hasMore}; empty owned node returns quizzes:[]. |
| GET | /{quizId} | QuizDefinition for authoring, including correctOptionIndex. |

**Authoring DTOs:** POST accepts exactly `{title,questions:[{text,options:[string],correctOptionIndex}]}`; PUT has the same required full definition plus required positive Int32 expectedRevision. correctOptionIndex is zero-based and must be within that question's array. Requests accept no child IDs, multiple IsCorrect flags, ownership or timestamps. QuizSummary is `{id,title,contentRevision,createdAtUtc,updatedAtUtc}`. QuizDefinition adds knowledgeNodeId and ordered questions `{id,text,position,options:[{id,text,position}],correctOptionIndex}`. ID/order/index consistency is validated; no partial question/option writes exist.

**Take DTO / key isolation:** QuizTake is `{quizId,title,contentRevision,questions:[{id,text,position,options:[{id,text,position}]}]}`. It contains no correctOptionIndex, IsCorrect/correctOptionId or other gabarito. Read the whole definition from one consistent projection/read snapshot so revision/questions/options cannot mix. Taking must not fetch/reuse an authoring DTO and hide its answers: before result, the key is absent from the taking client model/state, DOM and hidden attributes. The authenticated owner may read the key in authoring; this is a self-study UX boundary, not antifraud or secrecy against that owner.

**Submission/result DTOs:** PUT accepts exactly `{contentRevision,answers:[{questionId,selectedOptionId}]}`, with a positive Int32 revision and a bounded complete answer set. Reject score/correctCount/questionCount/percentage/correctOption/time/ownership/map/node/StudySession fields. QuizAttemptSummary is `{attemptId,quizId,quizTitle,contentRevision,submittedAtUtc,questionCount,correctCount,accuracyPercentage}`. QuizAttemptResult adds ordered answers `{questionId,position,text,options:[{id,position,text}],selectedOptionId,correctOptionId,isCorrect}`; quizTitle/text/options come from snapshots, isCorrect and percentage are derived. The response identifies the exact accepted attempt and answer set, without consulting the current definition for grading or labels. No current-state projection is mixed into this immutable result.

**Pagination/limits:** page defaults to 1 when omitted, minimum 1; pageSize defaults to 20 when omitted and accepts 1..100, without clamping. Invalid/duplicated/overflowing pagination returns 400 validation_failed. Quiz list order is CreatedAtUtc ASC, Id ASC; attempt history is SubmittedAtUtc DESC, AttemptId DESC. Read pageSize+1 to derive hasMore without a mandatory total COUNT. Parent validation/page and compound detail reads need a consistent request read snapshot; offset pages can shift/repeat/omit entries across requests, without cross-page snapshot isolation or cursor guarantees.

Authoring POST/PUT cap is 256 KiB (262144 bytes); submission PUT cap is 16 KiB (16384 bytes). Up to 30200 permitted text UTF-16 units need at most 181200 bytes under six-byte escaping, plus bounded definition envelope, fitting the authoring cap. The bounded ten question/option-ID pairs also fit the submission cap with escaping/headroom. Field limits remain independent; excessive whitespace/padding consumes the wire cap. Use native per-endpoint metadata plus actual bounded pre-JSON stream enforcement, including absent Content-Length, without unbounded buffering/temp files. Test real Kestrel fixed/chunked enforcement separately from TestServer; native framing can consume cap headroom. DELETE rejects an actual body without copying a body-cap policy to GET. Earlier endpoint limits remain unchanged.

Runtime take validation must reject answer-key-bearing payloads and copy only the permitted fields into taking state. Authoring and historical result validators have their own explicit key-bearing contracts; do not confuse them with QuizTake.

**Errors/security:** 400 validation_failed/csrf_invalid; existing sanitized 401/403 without HTML redirect; generic 404 quiz_not_found for missing/foreign/mismatched nested resources, including absent scoped attempts; 409 quiz_changed/attempt_id_conflict; sanitized no-store 413 validation_failed for oversize; 500 unexpected_error for operational failures, never relabeled as empty/missing data. Keep existing cookie/stamp/HTTPS and pre-controller sanitization. Strict own JSON contracts reject unknown, invalid/null and prohibited fields, following current infrastructure without claiming dedicated duplicate-JSON-property rejection. Error responses and logs must not contain private quiz/question/answer/key payloads, credentials, tokens/cookies, SQL/provider diagnostics or stacks; successful owned read/result DTOs expose only their authorized fields. No new secret/provider, CORS, JWT, sharing or validated endpoint-security claim exists at CP0.

**AttemptId/idempotency:** acquire the synchronous client submit lock before crypto.randomUUID(), generating one nonempty Guid per logical submission. Freeze its exact quiz/revision/answer set until resolved; navigation clears local presentation without proving rollback. Semantic equality is QuizId + ContentRevision + the set of questionId/selectedOptionId pairs; JSON answer order is irrelevant, and repeated question IDs are invalid. Same ID/same semantic payload returns the original full result and server SubmittedAtUtc without a second attempt or recalculation. Same ID/different semantic payload returns 409 attempt_id_conflict without exposing another attempt's data. GET lookup is always scoped to the full owned chain; a global PK collision must not disclose foreign payloads. Different IDs represent different intentional attempts, even with identical answers. Hard deletion bounds the lifetime of idempotent history; no persistent generic idempotency registry is introduced.

**Official SQLite writers/concurrency:** definition create uses atomic persistence/FKs; delete uses a scoped atomic delete/cascade. For definition update and submission, acquire a short same-connection BEGIN IMMEDIATE before ownership/definition/result reads and enlist EF. Resolve ownership first. Submission checks an existing AttemptId before checking the current quiz revision, allowing an already committed old-revision attempt to replay unchanged after editing. Only a new submission requires the current revision; validate, grade, copy all snapshots and persist counts/answers/options atomically before commit. Definition replacement compares expectedRevision and replaces children/revision/time in the same transaction. Rollback must leave no partial definition/result or tracked losing candidates. Provider failures/lock contention remain sanitized operational errors with no automatic lock retry.

| Race | Required behavior through official writers |
| --- | --- |
| Edit then Submit | A new old-revision submission returns quiz_changed without result; a committed old AttemptId may replay. |
| Submit then Edit | Result snapshots/counts/time commit first and remain unchanged after the edit. |
| Submit/Submit, same ID | Same payload converges on one result; different payload conflicts, with no partial children. |
| Submit/Submit, different IDs | Both valid intentional attempts may commit; neither overwrites the other. |
| Delete then Submit | Missing owned quiz returns generic not-found; no resurrection. |
| Submit then Delete | Result commits then is removed by the allowed cascade; no partial cascade/orphan remains. |

Native lock acquisition may be synchronous with limited cancellation; keep transactions short and check cancellation around acquisition and during supported operations. These rules do not promise correctness for arbitrary SQL, external writers, PostgreSQL or distributed hosts. They add no general optimistic-concurrency/idempotency framework, realtime or global in-memory lock.

**Ambiguous reconciliation:** a submission failure without a received HTTP response and with unknown outcome initiates scoped GET lookup for the same AttemptId. Compare quiz/revision/complete selected-answer set, not just HTTP 200 or counts: a match confirms the original attempt; divergence conflicts. Lookup 404 does not prove rollback of a delayed original request and offers only an explicit retry of the same ID/payload. Lookup failure retains recoverable pending identity, not fabricated success or a fresh ID. A received HTTP response is a deterministic protocol/transport outcome; an unknown/invalid body must not automatically trigger lookup. HTTP 500 or an invalid response still does not prove rollback or permit automatic PUT replay; provide explicit result verification before another deliberate action. No write is automatically replayed after network, CSRF, 401, protocol or operational failure.

**Frontend direction — planned:** Edit map adds a Quizzes section with paginated list/create/full edit/confirmed delete; View provides available quizzes, answering, result and history. Keep authoring and taking models/mounts separate; take never preloads the authoring key. Local drafts, radio selections, loading/empty/error, incomplete/submitting/result, changed-quiz and unresolved-send states are scoped by node/map/quiz/revision/visit. Use native fetch/runtime validation, session-private CSRF, context/request identity and AbortController for reads; obsolete results cannot overwrite another visit/account. Authoring reuses the editor mutation lock; submission locks synchronously before ID generation. Writes may commit after leave, so do not treat abort as rollback. Existing map URL/History remains; no router, browser-storage authority, polling or new dependency is added. Native fieldset/legend/radios, labels, contextual errors, status/focus transitions and responsive wrapping support keyboard/mobile. Future checks must distinguish controlled harness, browser smoke, full accessibility and physical touch evidence.

**Alternatives:** a KnowledgeContent subtype or generic Assessment/activity hierarchy adds coupling without need; incremental question/option PATCH increases partial-definition states; a persisted active attempt/draft adds unapproved lifecycle/resume behavior; grading against the latest definition loses version meaning; storing only selected/correct text loses other presented alternatives; copying current child FKs into history breaks edits; automatic retry/new IDs risks duplicate results. Prefer the specific bounded relational model and immutable result. No separate scheduler, ReviewState or StudySession relation is needed.

**Consequences/future considerations:** snapshots increase storage but retain the actual question and alternatives without version-table or generic JSON infrastructure. Atomic grading and explicit IDs make uncertain writes recoverable, while whole-definition replacement can reject an in-progress answer after an edit. Hard delete intentionally loses history; there is no permanent audit or production-retention guarantee. Attempt accuracy is point-in-time performance, not mastery/proficiency/completion. Phase 9 may consume results through separately reviewed metrics. Other question types, persisted drafts, granular editing, account cleanup, analytics, provider transition and broader testing/deployment choices require later scope and design. Package manager remains open.

**Checkpoints/acceptance:** CP0 design only, CP1 Quiz foundation + authoring/read backend, CP2 Submission/grading/history backend, CP3 Frontend authoring + answering/history, CP4 Integrated validation/closure. Each later checkpoint needs explicit authorization. See [Development](DEVELOPMENT.md#phase-8---assessments-design-baseline) for scope/exclusions/exits, future acceptance matrix A-R, validation and risk register; no criterion is marked PASS by design acceptance.

**Out of scope:** multiple correct answers, free-text/discursive questions, manual grading, question banks/imports/media/Markdown/HTML/hints/explanations, formal exams, teacher/student model, paid paths, timer/timeout/autosave/persisted draft/start attempt/pause/resume, randomization/adaptive testing, weighted/partial/penalized scoring/pass-fail thresholds, mastery/proficiency/node completion/Phase 9 aggregates, AI generation/recommendations, schedulers/FSRS/SM-2, gamification, StudySession integration, realtime/social/marketplace, native mobile/offline sync, PostgreSQL infrastructure, graph DB/distributed infrastructure or a new framework/dependency.
