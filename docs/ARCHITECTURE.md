# Architecture

## Phase 6 - Study Sessions design baseline

Complete, approved and published for the scoped Study Session workflow under [ADR-014](DECISIONS.md#adr-014---study-session-ownership-lifecycle-and-active-session-invariant). Checkpoint 1 foundation/read, AddStudySessions migration and node/map delete protection (881d12a), checkpoint 2 lifecycle/active backend and official transactional invariant (29ba218), and checkpoint 3 frontend (493d39a) are approved and published. Integrated closure was approved and published in 6045391 after validation on 2026-10-19. The implemented boundaries and limitations below remain unchanged. Phase 7 design is accepted under ADR-015; implementation remains planned / not started and requires a separate scoped request.

KnowledgeNode 1 → N StudySession records private study effort. Ownership follows ICurrentUser → existing account → PersonalWorkspace → KnowledgeMap → KnowledgeNode → StudySession. The session has only persisted Id (Guid), KnowledgeNodeId (Guid), StartedAtUtc and nullable EndedAtUtc; no direct owner/workspace/map ID or KnowledgeContentId is added. Duration and active/completed status are derived. Completed means the time record ended, never content/node completion or mastery.

Application obtains authoritative server UTC timestamps through TimeProvider. Domain.Start generates identity and an active record; TryComplete rejects an end before start without mutation and preserves an already completed record. Domain owns no clock. DateTimeOffset remains the Domain/API representation, with explicit UTC DateTime storage conversion for SQLite. Duration is EndedAtUtc minus StartedAtUtc; zero is valid. No separate creation/update/completion timestamp, persisted duration/status, notes, source, client timestamp, heartbeat, sort key, RowVersion or generic JSON payload is added.

At most one session may have EndedAtUtc null per PersonalWorkspace, across nodes and browsers. IStudySessionStore.StartAsync is a specific atomic operation. It opens the DbContext SQLite connection, calls Microsoft.Data.Sqlite 10.0.12 BeginTransaction(deferred:false), which emits BEGIN IMMEDIATE, and enlists EF with UseTransactionAsync. Ownership validation, workspace-wide active check, insert and persisted-response projection occur inside that short transaction before commit. Conflicts/failed operations roll back on disposal; the candidate is detached and the connection reference released. The synchronous provider lock wait uses its configured DefaultTimeout and checks cancellation immediately before/after acquisition; EF/SQL operations receive cancellation. No generic transaction wrapper, static semaphore or duplicated WorkspaceId is introduced. The official start path guarantees the invariant; arbitrary external SQL INSERTs are not covered by a declarative constraint. Busy/timeouts remain operational failures, never active_session_exists. PostgreSQL requires a later explicit request and a reviewed replacement for this concurrency strategy.

Implemented StudySessions persistence uses Id as PK, required KnowledgeNodeId FK with Restrict, CHECK (EndedAtUtc IS NULL OR EndedAtUtc >= StartedAtUtc), and history index (KnowledgeNodeId, StartedAtUtc DESC, Id DESC). AddStudySessions adds only this table and its constraints/index. Duration and Status are explicitly excluded from persistence; no auxiliary open-session or unique-by-workspace index is added. Startup never migrates, creates or seeds a database.

Browser close, refresh, navigation, logout, connection loss and device suspension leave the session open. Recovery offers Continue, Complete now or explicit Discard. Forgotten sessions can remain open for hours/days; their times cannot be corrected retroactively. Completed records are immutable except for confirmed hard deletion; discarding an active record hard-deletes it and permits a new start. There is no heartbeat, timeout, pause/resume, beforeunload completion, automatic close, archive, restore or soft delete.

Study history is persistent personal data, not an immutable audit log. Checkpoint 1's FK prevents cascading session deletion. Existing graph delete operations return 409 node_in_use for a node with any active/completed session and 409 map_in_use for a map containing such a node. Prechecks and confirmed FK failure classification preserve existing edge/ChildMap blockers, while database restrictions prevent partial cascades. Checkpoint 2 permits explicit hard deletion of owned active/completed sessions, releasing the history blocker when the last session is removed. Existing KnowledgeContent cascade semantics in ADR-013 remain unchanged for otherwise permitted deletions.

ListStudySessionsForNode and GetStudySessionForNode reuse the current-account/lazy-workspace resolver. IStudySessionReader filters workspace/map/node/session in SQL with no tracking; list checks its parent and reads a bounded page in one read snapshot, while detail uses one scoped projection. GET /api/maps/{mapId}/nodes/{nodeId}/study-sessions returns completed records only in sessions/page/pageSize/hasMore; GET .../{sessionId} may also read an active session, with endedAtUtc/durationSeconds null. DTOs contain only id/knowledgeNodeId/startedAtUtc/endedAtUtc/durationSeconds. Missing/foreign/mismatched resources return study_session_not_found, invalid/overflowing pagination validation_failed. page defaults to 1 and must be at least 1; pageSize defaults to 20 and accepts 1..100 without clamping. SQL reads pageSize + 1 after offset to derive hasMore without COUNT. Private results are no-store; GETs require existing authentication but no CSRF. Operational/native-stamp failures retain sanitized 500 behavior. The read snapshot is not a snapshot across pages or a start/write concurrency mechanism.

Checkpoint 2 implements the remaining backend routes in ADR-014. POST collection returns 201 with the persisted DTO and detail Location; POST .../{sessionId}/complete returns 204, including repeats, and DELETE .../{sessionId} returns 204 (repeat delete is 404). Complete uses a SQL-scoped conditional UPDATE with EndedAtUtc IS NULL and StartedAtUtc <= server now; the first successful update fixes the end. A zero-row update rereads the scoped record to distinguish already completed, missing and clock conflict. Delete is a scoped atomic SQL DELETE, with no resurrection on complete/delete races. All writes use existing auth/CSRF/no-store, accept no business body (any actual body is validation_failed), and introduce no 32 KiB metadata or automatic replay. Operational/native stamp failures remain sanitized 500, and a lost write response can be ambiguous.

GET /api/study-sessions/active needs authentication but no CSRF and returns {active, serverTimeUtc}; active is null when absent, otherwise {session, mapId, nodeId, nodeTitle}. The nested session uses the existing DTO; nodeTitle is current, and context/server time are projections, never persisted. A single SQL-scoped read excludes completed/foreign sessions; multiple active records from an unsupported writer fail closed rather than choosing one silently. No new index/schema/migration is required. Implemented history ordering remains StartedAtUtc DESC then Id DESC, without COUNT or a snapshot guarantee across pages. Checkpoint 3's implemented frontend provides a global authenticated-shell indicator, presentation-only timer, node start actions including View mode, recovery and paginated completed history with confirmed deletion. Navigation/logout do not close records; no duration aggregate or learning-completion measure is approved.

Checkpoint 3 uses own runtime-validated Study Session DTOs and the existing session-private CSRF client. StudySessionProvider lives above map/node visits, scoped by authenticated user/workspace. A small Study Session coordinator owns active reads and one synchronous study-mutation lock; React Context exposes it to the indicator and node section, and useSyncExternalStore subscribes to stable snapshots. Mount/login/F5, window focus and explicit writes revalidate active state with AbortController/request identity; focus requests are deduplicated. Unmount/logout aborts local I/O and discards local state only, without a study mutation or rollback claim. Every mutation checks current active state first, sends at most one write, then revalidates; conflict/network/5xx/protocol ambiguity never resends a write. Read/auth errors preserve recoverable UI and reuse existing session revalidation.

The timer recomputes elapsed from serverTimeUtc plus local wall-clock elapsed since reception, minus persisted StartedAtUtc, clamped visually at zero. A local one-second interval only renders; it never persists ticks or duration. Focus reanchors from the server; there is no continuous polling, WebSocket or browser-storage authority. Return to concept uses existing map History navigation, selects the node and focuses its heading. Node history consumes the real sessions/page/pageSize/hasMore envelope, requests pages of 20, appends in server order and removes repeated IDs when offset pages shift. Its per-node coordinator aborts obsolete reads and ignores old results; completion/deletion or active revalidation refetches page one. Offset omissions/shift remain a documented backend limitation, without a cross-page snapshot claim.

Own discriminated Note/Link DTOs and runtime validators reject invalid IDs/types/timestamps/payloads before retaining only contract fields. Each read has AbortController, cleanup and render identity; node/map/session changes discard obsolete data/drafts. Reads revalidate session once on 401 without replay. No preview/fetch/iframe exists. Content read/write failures preserve the shell/map; csrf_invalid invalidates the private token and no write is replayed after CSRF, 401, network or 500. Ambiguous results require checking current state before another explicit attempt. No backend, migration, dependency, new framework or broader concurrency policy is introduced.

CreateKnowledgeContent, UpdateKnowledgeContent and DeleteKnowledgeContent reuse validated current-account/lazy workspace resolution and a separate IKnowledgeContentStore. Native 32 KiB metadata covers all three actions as in graph authoring; TestServer metadata checks do not establish Kestrel enforcement. No new token, automatic replay, schema/migration, dependency or frontend source change is introduced. Existing node/map conflicts and cascades remain. Modified-column last-committed-write behavior remains without ETag/rowversion; disjoint changes can merge and timestamps are not commit ordering.

## Phase 4.4 - Authoring UX

Complete, approved and published in `c427c6e` over the unchanged Phase 4.2 contracts. MapWorkspace owns per-visit visual state and explicit edit mode; KnowledgeGraph receives callbacks and performs no HTTP/auth/ownership work. MetadataForm holds local drafts, CreateMap handles the empty/picker entry, and knowledgeMapAuthoringApi translates own request/201 DTOs, validates responses and uses the existing native-fetch transport. No new dependency or architecture ADR is needed.

The per-hook session client exposes a CSRF-protected action using its existing private in-memory token lifecycle. Every authoring attempt renews CSRF, sends one mutation and never replays automatically, including csrf_invalid, 401 and ambiguous network/500 responses. Login/logout policies stay unchanged. A 401 invokes existing session revalidation; a valid session retains a recoverable error and explicit retry.

Creates wait for validated 201; metadata/deletes wait for 204 before updating local state. PATCH sends only changed metadata, with explicit clearDescription/clearChildMap. Child choices come from current-workspace discovery; self links, cycles, self edges and duplicate edges follow backend rules. Initial node position is the predictable (node count × 240, 0), without a layout engine. Edit-mode drag stays local until stop; the PATCH translates only finite x/y, stores the confirmed position and rolls back on failure. Keyboard movement has an explicit Save position action. View-mode movement remains temporary.

One mutation per mounted editor is admitted synchronously; controls and dragging are disabled while pending. Per-node position versions and per-mount completion guards prevent old responses overwriting a newer visit. Sent writes are not aborted on navigation, because abort cannot establish rollback; completions from an unmounted editor are ignored. Returning to the picker refetches server-ordered discovery, keeping create/rename/delete summaries authoritative without a persistent cache. Drafts may be discarded by navigation; no unsaved-change blocker or cross-tab concurrency guarantee is introduced. Reopen/reload reconciles ambiguous outcomes. The original URL/History strategy remains.

## Phase 7 - Flashcards design baseline

The design is accepted under [ADR-015](DECISIONS.md#adr-015---node-owned-flashcards-and-review-progression). Implementation remains planned / not started and needs a separate scoped request. No source, migration, dependency or database change is authorized by this design checkpoint.

Flashcard is its own Domain entity with a required immutable KnowledgeNodeId (Guid), server-generated Id (Guid), Front, Back, ContentRevision (positive .NET Int32 / JSON integer), immutable CreatedAtUtc and server-owned UpdatedAtUtc. It is not a KnowledgeContent subtype and does not require or reference Note/Link. Ownership is ICurrentUser → existing account → PersonalWorkspace → KnowledgeMap → KnowledgeNode → Flashcard; persist no owner/workspace/map IDs. Front and Back are required plain text bounded to 2,000 and 4,000 .NET UTF-16 code units respectively. Reject empty/whitespace-only values; preserve submitted whitespace and newlines without trimming or Unicode/case/newline normalization, and render escaped text only. No Markdown/HTML, title, hint, tags, media, source, explanation or generic JSON is included.

ContentRevision exists from Checkpoint 1, starts at 1 and increments once when Front or Back differs by ordinal comparison of the final persisted strings. A material edit updates UpdatedAtUtc and, from Checkpoint 2, deletes the optional ReviewState row in the same atomic operation: the card projects 0 reviews, 0 correct and null last-reviewed and returns to never-reviewed. Historical events retain their answered revisions. Empty/material no-op PATCH is 400 validation_failed without save, timestamp/revision change or state reset, following Phase 5's content precedent. Revision overflow fails without mutation/wrapping. The official SQLite edit path reads the current card under BEGIN IMMEDIATE and commits text/revision/reset together, serialized with reviews; concurrent edits cannot lose a revision increment. This is not a generic rowversion/ETag or CRUD concurrency framework.

FlashcardReviewState is optional one-to-one current-revision state with FlashcardId PK/FK, ReviewCount, CorrectCount and LastReviewedAtUtc, created on first accepted review of that revision. Invariants are ReviewCount >= 1, 0 <= CorrectCount <= ReviewCount and a non-null last-reviewed instant. Absent state projects 0, 0, null. Materializing these derivable values avoids repeated event COUNT/aggregation for progress and rotation. FlashcardReview is immutable: ReviewId (client-generated nonempty Guid), FlashcardId (Guid), ContentRevision (positive Int32 actually answered), Result (Domain Correct/Incorrect; stable stored/JSON `correct` / `incorrect`) and server-generated ReviewedAtUtc. Event insert/state create-update are atomic. No LastResult duplicate, DueAtUtc, interval, ease or scheduler state is stored.

Phase 7 has no spaced-repetition scheduler. A node-scoped LEFT JOIN selects first cards without state ordered CreatedAtUtc ASC, Id ASC, then reviewed cards ordered LastReviewedAtUtc ASC, CreatedAtUtc ASC, Id ASC. Never-reviewed cards, including new/edited ones, intentionally take priority while any remain. All cards stay eligible; after an answer, next recalculates from persisted state. Empty nodes return item null; all-reviewed nodes still return a card, and a single card can immediately reappear. No deck-complete state, persistent queue, backend study run, client round tracking, batch or exact cursor exists; users leave when they wish. Refresh/navigation resumes the current rotation rather than a saved run. Correct/Incorrect is self-reported recall, not mastery. Historical events remain while the card exists; no review-history listing or analytics endpoint is included.

Use explicit planned migrations only: `AddFlashcards` for content/revision, then `AddFlashcardReviews` for state/events. Store DateTimeOffset UTC in Domain/API with the established explicit SQLite UTC DateTime conversion. Flashcards has KnowledgeNode FK Cascade, positive ContentRevision CHECK and (KnowledgeNodeId, CreatedAtUtc, Id) index; Domain/API enforce text limits. ReviewState has FlashcardId PK/FK Cascade, count/last-time checks and (LastReviewedAtUtc, FlashcardId) order index. Reviews has ReviewId PK, FlashcardId FK Cascade, positive ContentRevision and stable-result CHECKs, and (FlashcardId, ReviewedAtUtc DESC, ReviewId DESC) index for scoped events/cascade. Historical event ContentRevision is not an FK to the card's changing revision. No owner duplicates, PostgreSQL/graph storage or startup migration/seed is added.

Node/map ownership and deletion remain nested and server-derived. Explicit card hard delete also deletes its review state/events; deleting an otherwise deletable node cascades cards and their review data, so cards alone do not produce node_in_use/map_in_use. Existing blockers remain: notably StudySession still blocks node/map deletion. The UI must make the irreversible card deletion explicit.

Authoring uses authenticated nested GET collection/detail, POST create, PATCH Front/Back and DELETE detail under `/api/maps/{mapId}/nodes/{nodeId}/flashcards`. Omitted PATCH fields remain; unknown/null/blank supplied values and empty/no-op patches are validation_failed. Successful PATCH/delete return 204; create returns 201 with FlashcardDto and detail Location. FlashcardDto is `{ id, knowledgeNodeId, front, back, contentRevision, createdAtUtc, updatedAtUtc }`; own request DTOs contain no IDs/timestamps/ownership. GET list is `{ flashcards: [{ card: FlashcardDto, reviewState: { reviewCount, correctCount, lastReviewedAtUtc } }], page, pageSize, hasMore }`; detail is FlashcardDto only. page defaults to 1 and must be >= 1; pageSize defaults to 20, accepts 1..100 and is not clamped. Invalid/overflowing values are 400 validation_failed. SQL orders CreatedAtUtc ASC, Id ASC and reads pageSize+1 after offset for hasMore without mandatory COUNT; parent/page reads share one snapshot. Offset pages may shift/repeat/omit entries across requests. All reads/errors are authenticated/no-store without CSRF; all writes/errors use existing native CSRF/no-store.

Phase 7 writes use a 64 KiB (65,536-byte) native body cap, not 32 KiB: 6,000 UTF-16 units at six-byte Unicode escaping need at most 36,000 bytes, leaving ample room for property names and the fixed JSON contracts. Every allowed Front/Back value fits even with maximal escaping. Excessive JSON padding still consumes this cap; field validation remains independently required. Existing Phase 4/5 limits are unchanged. Verify real-server enforcement during implementation, without treating TestServer metadata as proof.

GET `/api/maps/{mapId}/nodes/{nodeId}/flashcards/study/next` returns 200 `{ item: null }` or `{ item: { card: { id, front, contentRevision }, reviewState: { reviewCount, correctCount, lastReviewedAtUtc } } }`, never Back. Explicit Reveal alone requests GET `/api/maps/{mapId}/nodes/{nodeId}/flashcards/{flashcardId}/study/reveal?contentRevision=R`; the observed positive Int32 query value is required exactly once. A consistent scoped projection returns 200 `{ flashcardId, back, contentRevision }` only when the card is still R, otherwise 409 flashcard_changed without Back. Invalid revision is 400 validation_failed, missing/foreign/mismatched paths are generic 404 flashcard_not_found. Do not prefetch/reuse authoring Back in study mode. This is a study UX boundary, not secrecy against an authenticated owner with authoring access.

PUT `/api/maps/{mapId}/nodes/{nodeId}/flashcards/{flashcardId}/reviews/{reviewId}` accepts `{ result: "correct" | "incorrect", contentRevision }`. First commit and idempotent replay return 200 `{ review: { reviewId, flashcardId, contentRevision, result, reviewedAtUtc }, currentReviewState: { contentRevision, reviewCount, correctCount, lastReviewedAtUtc } }`. GET on that same route is a scoped read with the same envelope; missing/foreign/mismatched reviews return generic 404 flashcard_not_found. Never read a ReviewId outside the ownership chain. Event fields and original server time are immutable; currentReviewState is a consistent current-card projection, not an original-write snapshot. Later reviews/edits can advance/reset it; no extra event snapshot columns are needed. A 200 matching the pending card/revision/result confirms an ambiguous write; mismatch is a conflict. A lookup 404 allows only explicit retry of the same ID/payload, since a delayed original request may still commit. Lookup errors preserve an unresolved state. Never automatically replay or substitute a new ReviewId.

The client acquires its synchronous mutation lock and creates one nonempty Guid ReviewId on Correct/Incorrect before the first request, keeping ID/card/revision/result until resolution, not generating it on reveal. Equality is exactly FlashcardId + ContentRevision + Result. Same-ID/same-payload replay returns the original event/ReviewedAtUtc without a new event, increment or LastReviewedAtUtc change; different semantic data is 409 review_id_conflict without foreign details. New stale submissions are 409 flashcard_changed. The official SQLite writer uses same-connection BEGIN IMMEDIATE before reads: resolve ownership, replay/check ReviewId before comparing current revision, otherwise validate revision, insert event and update state before atomic commit. Thus an old confirmed event can replay after an edit without restoring old progress. Same-ID concurrent requests make one event/state transition; different IDs serialize and both count without lost updates, including across tabs. currentReviewState may reflect later operations, without changing that immutable event. Card deletion/review races obey SQLite/FKs and do not resurrect data. Native lock waits may be synchronous and cancellation limited; busy remains operational without automatic retry. No generic idempotency/global lock, realtime/distributed, arbitrary-writer or PostgreSQL guarantee is introduced.

The frontend reuses current React/native-fetch patterns: NodeDetails Edit map has paginated authoring and confirmed delete; View offers Study without preloading Back. Refetch authoring page one after writes. Continuous study has loading/no-cards/prompt/revealed/submitting/next/error-retry/leave actions, never completed-deck UI. Explicit Reveal is a request, not just hiding answer text; unrevealed Back is absent from the DOM/accessibility tree. A scoped hook/coordinator uses AbortController/request identity for list, next, reveal and review lookup; navigation/logout discards obsolete results/local UI without proving a sent write rolled back. flashcard_changed discards stale prompt/answer, informs the user and fetches next; flashcard_not_found refetches next without resurrection. A later submission rechecks revision after reveal; retry/answer always requires explicit intent. Native labeled buttons/focus and touch-friendly single-column controls support keyboard/mobile without hover or required shortcuts. No router, store or dependency is introduced.

No StudySession is required, linked or automatically created. Reviewing is represented by FlashcardReview; Phase 6 time tracking remains a separate, user-initiated workflow. Do not claim study time from review duration.

## High-level responsibilities

- **Frontend:** presents knowledge maps and learning workflows, handles visual interaction and navigation, and communicates with the API.
- **API:** exposes REST operations and translates requests and responses at the application boundary. Business logic must remain outside controllers.
- **Application/domain:** implements use cases and business rules, including the knowledge graph and learning concepts.
- **Infrastructure:** supplies technical integrations and environment-dependent capabilities required by the application.
- **Persistence:** stores and retrieves application data using EF Core and the explicitly selected database provider.

The authorized Phase 2 skeleton uses `Talynor.slnx`, with Api, Application, Domain, and Infrastructure projects under `src/backend`, and UnitTests and IntegrationTests under `tests`. Application references Domain; Infrastructure references Application; Api references Application and Infrastructure for host composition. UnitTests references Domain and Application; IntegrationTests references Api. Infrastructure has no direct Domain reference. This initial responsibility split does not finalize product module boundaries or broader implementation patterns.

`global.json` selects SDK 10.0.401 with `latestPatch` roll-forward and prerelease SDKs disabled. `Directory.Build.props` enables nullable reference types and implicit usings without treating all warnings as errors. ## VS-001 read-only validation slice

`GET /api/knowledge-maps/{mapId}` returns `software` or `csharp` (200), or 404 for an unknown ID. The API explicitly maps Application read projections to its own HTTP contracts: map id/title/description/nodes/edges, node id/title/description/progress/studyMinutes/childMapId, and edge id/sourceNodeId/targetNodeId. No coordinates, visual styles, relationship taxonomy, or XYFlow types are exposed.

`GetKnowledgeMap` delegates to `IKnowledgeMapReader` in Application. `InMemoryKnowledgeMapReader` in Infrastructure supplies fixed demonstration content; its externally visible collections are read-only. Domain intentionally remains without artificial models. The reader is registered as a singleton and the use case as scoped. Cancellation propagates through the controller and use case to the reader.

## Phase 3.2B.1 - Account registration

`POST /api/auth/register` accepts an independent email/password DTO. The API validates structure and UTF-16 limits, applies the existing native antiforgery filter, and rejects an already authenticated request with 409. `RegisterUser` in Application trims only the email and delegates account creation to `IIdentityAccountService.CreateAsync`; 3.2B.2B adds only an account lookup by ID. Its specific Success/Invalid/Duplicate results contain no HTTP, Identity, EF, or SQLite types. Domain remains unchanged.

`IdentityAccountService` in Infrastructure creates `IdentityUser` through `UserManager.CreateAsync`. Email and username receive the same trimmed value, with Identity owning normalized fields. The adapter translates known Identity validation results; only SQLite's specific single-column UNIQUE failure on `AspNetUsers.NormalizedUserName` is translated into a concurrent duplicate. PK, busy, other constraint failures, and unknown validation failures remain operational errors. The existing migration/model is unchanged.

Success is 201 without body, Location, auto-login, or auth cookie. Duplicate registration returns generic 400 `registration_failed`; input/policy failures use 400 `validation_failed`, and operational failures use sanitized 500 `unexpected_error`. An endpoint-only result filter sanitizes automatic model-binding errors and translates native antiforgery failure to 400 `csrf_invalid`. Registration responses are no-store and use native ProblemDetails/ValidationProblemDetails; no global exception or request middleware is introduced for registration.

The native registration policy remains five requests per ten-minute fixed window per remote IP, no queue; the separate login policy is described below. IPv4-mapped IPv6 is normalized; absent IP uses a shared restricted partition. Forwarded headers are not trusted. Pipeline order is HTTPS redirection, routing, authentication, authorization, rate limiting, and controllers. An admitted request consumes quota before MVC validates CSRF/input. Rejection is 429 `rate_limited`, with Retry-After when available. The action's native request-size limit is 8 KiB on servers supporting that feature; TestServer is not a real Kestrel/body-limit verification.

The account/password policy and local-use limitations are recorded in ADR-008 and SECURITY.md. No login, logout, me, current-user abstraction, login limiter, custom lockout, frontend change, or SecurityStampValidator change is included in registration. The separately reproduced rejection-path incompatibility is addressed below.

## Phase 3.2B.2A - Security Stamp compatibility

Identity 10.0.12's native validator explicitly signs out `Identity.TwoFactorRememberMe` after rejecting an invalid stamp. With that handler absent, a real cookie/SQLite/SignInManager test reproduced an InvalidOperationException after the default 30-minute validation interval. The approved correction uses only the official `AddTwoFactorRememberMeCookie()` helper alongside `AddApplicationCookie()`. `Identity.Application` remains the sole application authentication scheme and the default for authenticate, challenge, forbid, and sign-in; `Identity.TwoFactorRememberMe` is a technical auxiliary sign-out handler. No External or TwoFactorUserId scheme is registered.

The native `SecurityStampValidator<IdentityUser>`, its callback, 30-minute interval, and all application-cookie options remain unchanged. No Talynor flow issues the auxiliary cookie, and MFA is not implemented. Native auxiliary-cookie defaults are retained; they do not replace the application-cookie policy. Regression tests use real cookies, UserManager stamp updates, and a test-only TimeProvider: a valid stamp remains authenticated and is renewed by the native validator; an invalid stamp after the interval returns 401 without exception, deletes cookies, and rejects replay of the original ticket. Both diagnostic routes exist only in the test factory and return 404 in the normal API host. No schema, dependency, frontend, or session endpoint change is introduced.

## Phase 3.2B.2B - Session Flow

`LoginUser`, `GetCurrentUser`, `ICurrentUser`, and `ISessionService` belong to Application and expose only own projections/results. `IdentitySessionService` is scoped in the API because native SignInManager needs the current HTTP response; it finds the Identity account by email and calls `PasswordSignInAsync` with isPersistent=false and lockoutOnFailure=true. Missing accounts and native authentication failures share InvalidCredentials; operational exceptions propagate to sanitized HTTP 500. There is no extra logout use case: the authorized controller delegates to the session adapter without ceremonial orchestration.

`HttpCurrentUser` is scoped in the API and reads IHttpContextAccessor. Missing context, anonymous identity, missing/blank/duplicate NameIdentifier, or multiple authenticated identities yield false/null. Email is never an identity fallback. `/me` uses this ID and the minimal `IIdentityAccountService.GetByIdAsync` extension; Infrastructure reads current Identity data and returns AccountSummary, never IdentityUser. Missing accounts/invalid IDs result in 401 and local sign-out; database errors do not become missing accounts.

Native exception handling is restricted to login/me/logout and the current-workspace paths, before authentication middleware, so a database failure during native cookie/stamp validation also returns no-store 500 unexpected_error rather than raw diagnostics. This is not a global handler or a replacement for SecurityStampValidator; registration and other endpoints retain their existing behavior. Controller-level operational failures use the same sanitized response.

A login-only response callback suppresses positive application-cookie renewal on failed login responses, including an already-authenticated 409 after the stamp interval. It preserves deletion headers and never changes the native validator/callback. Normal authenticated reads still allow native valid-stamp renewal.

Anonymous `POST /api/auth/login` accepts independent email/password input, trims only email, and validates format plus 256/128 UTF-16 maxima. Password is not normalized, truncated, or rechecked against creation policy. Success is empty 204 with the existing session cookie; native failures are uniform 401 invalid_credentials. An existing authenticated session returns 409 already_authenticated without account switching or cookie issuance. `GET /api/auth/me` and `POST /api/auth/logout` require Authorize. Me returns only id/email; logout uses native SignOutAsync and returns empty 204. All responses are no-store, including challenges (401 JSON) and forbids (403 JSON), with no redirects. The existing endpoint-only RegistrationProblemDetails filter is reused for session input/CSRF sanitization; its registration behavior is preserved.

Native lockout allows new users, uses five failures and a five-minute duration. Login has its own fixed-window policy of ten requests per minute per normalized remote IP, no queue, a shared missing-IP bucket, and no forwarded-header trust. Registration quota is unchanged. Login uses the native 8 KiB action limit where supported. Login/logout require the existing native CSRF filter; GET me does not. Clients must bootstrap a new request token after login/logout because identity changes, without assuming tokens are globally revoked or one-time.

Multiple browsers may hold independent sessions; a new login does not invalidate earlier sessions. Logout deletes the local browser cookie, not all tickets or other browsers. No session table, global revocation, or single-session enforcement is added. Unconfirmed email is explicitly permitted; no confirmation/reset sender or provider is introduced. The B.2A native validator and technical auxiliary handler are preserved without functional MFA or auxiliary-cookie issuance. Domain, EF model/migrations, production Data Protection, dependencies, and frontend are unchanged.

## Phase 3.3 - Personal Workspace and Ownership

Completed, approved, and published under [ADR-009](DECISIONS.md#adr-009---personal-workspace-and-ownership). `PersonalWorkspace` is the first Domain entity, containing only an application-generated Guid ID, immutable owner user ID string, and UTC creation timestamp. The scoped Infrastructure store uses EF Core/SQLite. `PersonalWorkspaces` has an explicit PK, required owner/time, and UNIQUE index on OwnerUserId. On the exact SQLite owner UNIQUE conflict, it detaches the losing candidate and rereads the winner; all other provider failures propagate. Anonymous/invalid/deleted-account sessions return sanitized 401; absent accounts cause local sign-out. Operational failures, including native stamp validation before the controller, remain sanitized 500. The existing restricted exception handler now includes only this additional endpoint. This approved GET can initialize an empty personal workspace; it has no client-controlled mutation payload or content CRUD. Login/logout CSRF and cookie protections are unchanged.

OwnerUserId is a logical Identity reference with no navigation/FK/cascade. ## Knowledge graph

Knowledge nodes and their relationships are domain concepts. A node may lead to another map, and relationships must eventually represent connections beyond a tree or folder hierarchy.

A graph-shaped domain does not require a graph database. ADR-011 defines the initial relational storage, positions, same-map edge endpoints and same-workspace drill-down. Broader cross-map behavior, cycle rules and relationship semantics remain open. Examples such as contains, prerequisite, related to, and depends on do not establish a final relationship taxonomy.

## Visual experience and early validation

The interactive graph experience is a primary technical risk. A dedicated frontend spike precedes the application skeleton to validate nodes, edges, zoom, pan, selection, drill-down, submaps, and navigation between knowledge levels.

SPIKE-001 validated custom nodes, edges, selection, dragging, zoom, pan, minimap, drill-down, TypeScript, basic responsiveness, and basic accessibility; build and lint passed. XYFlow / React Flow is now adopted as the initial graph visualization library, as recorded in [ADR-007](DECISIONS.md#adr-007---initial-xyflow-graph-visualization). Larger graph performance, touch behavior on real devices, and full accessibility remain to be validated. Adoption can be reevaluated if concrete limitations emerge; no artificial node-count limit is defined.

XYFlow belongs exclusively to the frontend visualization layer. Domain and application logic, API contracts, and persistence must not depend on XYFlow-specific types or expose its Node/Edge structures. The spike's view types do not define domain entities or storage models. Final interaction design and automatic layout remain open; adoption does not finalize relationship semantics or persistence.

## Database strategy

SQLite supports the early development and prototyping stages. PostgreSQL is the production target.

Persistence should avoid unnecessary provider-specific behavior. This does not assume that the providers are interchangeable: provider changes must be explicit, reviewed, and validated, including their data and migration implications.

Migrations must be controlled. Do not provision PostgreSQL, configure a database, or create migrations during the foundation task.

Introducing PostgreSQL infrastructure requires an explicit request; advancing to another roadmap phase does not by itself authorize it.

## Testing and operations direction

- Use xUnit for backend unit and integration testing.
- Use Testcontainers when justified by the test's purpose.
- Define frontend automated testing later.
- Use structured logging and health checks.
- Introduce OpenTelemetry when justified.
- Use environment-based configuration and keep secrets outside source control.
- Enable C# nullable reference types when the application skeleton is created.
- Introduce GitHub CI later in the roadmap.

These directions do not authorize tooling installation or operational configuration in the current phase.

## Architecture principles and exclusions

Start with a modular monolith and prefer simplicity over infrastructure complexity. Keep architecture explicit and business logic out of controllers. Do not introduce a distributed architecture prematurely.

The initial scope excludes microservices, Redis, RabbitMQ, Kafka, Kubernetes, Elasticsearch, and graph databases. Background workers require later justification and approval. AI, marketplace, and social networking features are outside the initial product scope.

## Open design questions

Local ASP.NET Core Identity, cookie/antiforgery infrastructure, account registration/password policy, and Session Flow/lockout are approved under ADR-008; the initial personal workspace is defined in ADR-009 and persistent knowledge storage in ADR-011. Account recovery and verification, workspace lifecycle, and future workspace operations still require scoped implementation/design. Product module boundaries, automatic layout, final interaction design, relationship taxonomy, authoring concurrency, further business API contracts, frontend test tooling, package manager, deployment topology, and production migration procedures remain open. Migrations are explicit; PostgreSQL infrastructure remains unauthorized.

## Phase 4.2 - Map/Node/Edge Authoring Backend

Eight small Application use cases and IKnowledgeMapStore expose map/node create, PATCH and delete and edge create/delete over the existing schema.
