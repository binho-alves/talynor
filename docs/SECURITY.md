# Secure-development principles

## Phase 5 content foundation security

Private contents derive access only through the validated account, server-resolved workspace, map and node. Both nested content GETs require authentication, return no-store and accept no ownership override; foreign/missing/mixed paths receive the same 404 without existence disclosure. Reads do not require CSRF. Existing cookie/stamp, sanitized operational-error and local sign-out behavior remain. No content writes or frontend content UI are exposed.

Note is bounded literal plain text; no Markdown/HTML parser or active rendering is added. Link stores a bounded absolute HTTP(S) URL with host, without userinfo, controls, whitespace ambiguity or backslashes; internal URLs are intentionally allowed. BCL validation performs no DNS or server-side fetch, redirects, scraping or preview; storing a URL does not establish destination safety. Future UI must use safe explicit link navigation and React text rendering, without auth/CSRF/browser-storage persistence. Logs/responses must not expose private bodies or provider diagnostics.

The new content FK and CHECKs protect parent existence and discriminator/payload shape; Domain enforces UTF-16 limits and URL syntax. Permitted node/map deletion hard-deletes dependent content; existing edge/ChildMap blockers remain. Files/upload/storage, embeds, rich HTML, study features and new dependencies remain absent. ADR-013 records the future CSRF-protected authoring boundary and 32 KiB write limit; this increment adds no unsafe content endpoint or GET body-size metadata.

## Phase 4.4 authoring frontend

All graph writes use the existing authenticated nested API with native CSRF. The same per-session client renews a private in-memory request token immediately before each attempt; it is sent only in X-CSRF-TOKEN, never URL or JS storage. No auth cookie policy, backend authorization, JWT or workspace override is introduced. Ownership remains server-derived; a map GUID is not a secret. Foreign/missing 404 share safe local feedback, and invalid_child_map/invalid_edge_nodes disclose no ownership details.

No mutation is automatically replayed, including POST after ambiguous network/protocol/500 responses. csrf_invalid clears the cached token; the next explicit action renews it. Write 401 uses existing session revalidation without replay. Unknown diagnostics never render. Creates/metadata/deletes wait for valid success; deletion requires an explicit UI confirmation. map_in_use/node_in_use never trigger client-side cascading deletion. Position failures roll back the visual value, without claiming a failed/ambiguous response proves server rollback. Reload reconciles uncertain outcomes. Titles/descriptions remain React-escaped text; no HTML, credentials or map content are stored in browser storage. Sent writes may finish after navigation, but unmounted-editor callbacks cannot change the next view. Server authorization/constraints remain authoritative under races; no optimistic concurrency claim is made.

Phase 3 and Phase 4, including 4.1, 4.2, 4.3A, 4.3 and 4.4, are complete, approved and published. Frontend authoring is available under the protections above; anonymous demos remain separate from private maps and no account/map seed exists. Phase 5 — Knowledge Content is in progress with the approved Note/Link foundation/read protections above. Content authoring/frontend remain unimplemented and file-specific security/storage decisions remain open. No production-readiness claim is made.

## Secrets and configuration

- Never put passwords, tokens, connection credentials, private keys, or other secrets in source control.
- Keep secrets outside committed files and use an appropriate environment-specific delivery mechanism when implementation is scoped.
- Separate development, test, and production configuration. Do not silently fall back to development credentials or insecure production defaults.
- Use placeholders in documentation and examples; do not copy real secrets into command output or reports.

## Authentication and authorization

- Local Identity and browser cookies are approved under [ADR-008](DECISIONS.md#adr-008---incremental-local-identity-and-persistence). `Identity.Application` remains the sole application authentication scheme and default for authenticate/challenge/forbid/sign-in: `__Host-Talynor.Auth`, HttpOnly, Secure Always, SameSite Lax, Path `/`, no Domain, eight-hour ticket validity without sliding expiration. B.2B login uses non-persistent sign-in with no browser Expires/Max-Age. SecurityStampValidator remains wired, and challenge/forbid return sanitized JSON 401/403 with no-store, without redirects.
- 3.2B.2A registers only the additional technical `Identity.TwoFactorRememberMe` handler using native `AddTwoFactorRememberMeCookie()`. This fixes the reproduced missing-handler exception during Identity 10.0.12 stamp rejection. The native validator/callback and 30-minute interval remain unchanged; invalid stamps after the interval now return 401, delete cookies, and reject the original ticket. Within the interval, stamp changes are not yet revalidated. External and TwoFactorUserId remain absent. No Talynor flow issues the auxiliary cookie; deletion headers during rejection are not functional issuance. No MFA is implemented. Its retained native defaults are name `Identity.TwoFactorRememberMe`, HttpOnly, Secure SameAsRequest, SameSite Lax, no Domain, Path derived from request PathBase (`/` on the current host), 14-day ticket lifetime, and sliding expiration. These defaults do not weaken or replace the main cookie policy; functional use would require a separate security review. Tests use real SQLite/cookies with a controlled clock, and diagnostic endpoints exist only in the test factory, returning 404 in the normal API host.
- Native antiforgery uses header `X-CSRF-TOKEN` and `__Host-Talynor.Csrf` (HttpOnly, Secure Always, SameSite Strict, Path `/`, no Domain). Anonymous `GET /api/auth/csrf` returns only a request token with no-store. The cookie token is not exposed in JSON. The MVC controller filter skips GET and protects register/login/logout; missing, invalid, and mismatched-client tokens are rejected before the action. Obtain a new request token after login/logout to match the new identity. Registration does not change identity, so a new token after successful registration is optional. Tokens are not one-time/global revocation mechanisms and do not authenticate a user.
- There is no global fallback authorization policy. Health, demonstration maps, and CSRF bootstrap remain anonymous; OpenAPI remains Development-only. No CORS, rate limiting, JWT, account-specific password/lockout configuration, or current-user implementation is introduced by 3.2A.
- Review identity design when account workflows are scoped, including relevant credential, session, and account recovery behavior.
- Make authorization explicit for every protected operation, including workspace, node, content, study activity, and assessment access.
- Validate ownership and permissions on the backend. Client-side interface visibility is not sufficient authorization.
- Prefer fail-closed behavior when critical access decisions are ambiguous.

## Phase 3.2B.1 registration security

- Anonymous register creates an unconfirmed Identity account without auto-login. An authenticated request is rejected with 409; no implicit account switch, logout, or auth-cookie issuance occurs. Email=username after outer trim, RequireUniqueEmail=true, Identity normalization, and the existing unique NormalizedUserName index protect equivalent/concurrent registrations. No Gmail/provider rules are applied. Email is not proof of ownership or identity; any future ownership uses account ID.
- Email accepts at most 256 UTF-16 units after trim; password accepts at most 128 and is preserved exactly. Identity's minimum is 15 UTF-16 units with RequiredUniqueChars=1, without required uppercase/lowercase/digit/non-alphanumeric composition. Passphrases, spaces within passwords, and Unicode accepted by Identity are supported; Identity rejects whitespace-only passwords. There is no Unicode normalization, blocklist, external compromised-password service, or custom hash. UTF-16 length is not Unicode-code-point counting; this is not a full standards-compliance claim.
- Before public exposure, review compromised/common-password blocking, Unicode handling, hash cost, email verification/recovery, enumeration/timing, and full session/deployment protection. B.2B introduces native login/lockout below. EmailConfirmed stays false; no sender or confirmation endpoint exists.
- Duplicate response is generic 400 registration_failed, without duplicate_email/email_exists/username_taken or raw Identity details. Structural/policy failures use validation_failed; native CSRF failures use csrf_invalid. Unknown validation/provider failures are sanitized 500 unexpected_error, never relabeled as duplicate. Public registration responses are sanitized and do not include submitted email/password/token, provider diagnostics, or exceptions. Explicit logs added by the registration flow must not include submitted email/password/token or raw exceptions/provider diagnostics. Framework exceptions and diagnostics may still be emitted internally according to the logging configuration; sensitive data must never be deliberately logged. This slice does not introduce a global logging or redaction policy/framework. Generic errors still permit residual enumeration through registration success/failure and timing.
- The registration-only native limiter permits five requests per ten-minute fixed window per remote IP, QueueLimit=0. It normalizes mapped IPv4 and shares a restricted missing-IP bucket; forwarded headers are ignored. Middleware runs before MVC/CSRF: even rejected CSRF requests consume quota, and the sixth request can be 429 rate_limited before CSRF validation. NAT/proxies can share quota; counters are in-memory per instance and reset with the process. This is neither distributed protection nor comprehensive DoS defense. Fixed-window boundaries can permit bursts.
- The per-action native request-size limit is 8 KiB where the HTTP server supports the feature. Tests using TestServer do not establish actual Kestrel body-limit/TLS enforcement. All registration responses are no-store; requests/tokens/passwords must not be logged or embedded in shell history. Health, maps, and bootstrap remain anonymous and outside the registration quota.
- Registration remains unchanged by 3.2B.2A: 201 without auto-login, application-cookie issuance, or functional auxiliary-cookie issuance. The separate compatibility regression proves native stamp rejection rather than relying only on scheme-configuration assertions.

## Phase 3.2B.2B session security

- Login requires a native CSRF pair and applies its own native limiter: ten requests/minute per normalized remote IP, QueueLimit=0, shared restricted missing-IP bucket, no X-Forwarded-For trust. Registration's quota is unchanged and independent. An admitted request consumes quota before MVC/CSRF. Rejection is no-store 429 rate_limited with Retry-After when available. Fixed windows permit boundary bursts; counters are per process and reset; NAT/proxies share quota. Distributed/proxy protection is not implemented.
- Native PasswordSignInAsync uses isPersistent=false and lockoutOnFailure=true. New users have lockout enabled, five failures trigger five minutes, and success resets the counter according to Identity. Lockout can be abused to deny a known account access; IP limiting reduces attempts but is not comprehensive DoS protection. Public failures for missing account, wrong password, lockout, and not allowed are identical 401 invalid_credentials without counters/reasons. Compensatory hashing is deferred, so timing remains distinguishable. Registration success/failure also permits residual enumeration.
- Email is trimmed and validated with a 256 UTF-16 maximum; passwords are required/nonempty with a 128-unit maximum, preserved without trim/normalization/truncation or reapplying creation policy. The native 8 KiB login request limit applies where the server supports it. An authenticated login returns 409 without implicit logout/account switching. Errors use the existing endpoint-only sanitizer; operational errors become 500 unexpected_error, never invalid credentials. Added logs contain only generic operation names, without raw exceptions, input, credentials, or cookie/token/stamp values.
- Me/logout require Authorize and return no-store. Me uses a fail-closed unique authenticated NameIdentifier and reads current Identity account data by ID, returning only id/email. Missing account/invalid identifier causes local sign-out/401; provider failure is sanitized 500. Logout requires native CSRF and calls SignOutAsync; it removes the current browser cookie only. Other browsers remain authenticated, and a retained original ticket is not globally revoked by logout. No session table, global logout, or single-session policy is added.
- Login explicitly allows unconfirmed email; EmailConfirmed remains false. Email is not proof of ownership. No verification, reset, email sender, MFA, JWT, or CORS is introduced. The auxiliary TwoFactorRememberMe cookie is never issued by normal login. Native stamp validation still occurs after the 30-minute interval and can refresh the principal/cookie and IssuedUtc while preserving the original ExpiresUtc. With SlidingExpiration=false, the effective ticket deadline remains eight hours from the original login; stamp refresh is not sliding expiration and does not grant a new eight-hour window. Invalid-stamp rejection, expiry, and preservation of the original deadline after valid refresh are covered using real-login cookies and a controlled test clock, while the B.2A regressions remain unchanged.
- Browser/client CSRF tokens must be refreshed after login and logout. Old tokens from another identity cannot be assumed valid; the completed 3.4 frontend consumes them as described below. In-process tests use real Identity and migrated temporary SQLite, not EF InMemory or a Development database. They do not prove actual TLS/browser SameSite enforcement, Kestrel body limits, multi-instance protection, or production readiness.
- Native exception handling applies only to login/me/logout and the current-workspace endpoint and also sanitizes failures before controllers, including database outages during native stamp validation. It does not classify operational errors as credentials or customize the validator. Framework diagnostics may still be logged internally under the existing logging configuration; this slice does not introduce a global redaction policy.
- Failed login responses suppress positive application-cookie renewal even when the native validator has revalidated an existing session. The response callback applies only to login, preserves cookie-deletion headers, and does not replace native validation or normal successful-read renewal. No account switch or authentication-cookie issuance is allowed on a 409 login.

## Phase 3.3 personal workspace ownership

- Authorized `GET /api/workspace` resolves owner exclusively from the validated ICurrentUser ID; client query parameters/IDs cannot select an owner or another workspace. There is no endpoint for arbitrary workspace IDs. The current account is checked before workspace access, preventing access by already-removed accounts. Invalid/missing accounts cause local sign-out and 401; provider failures remain sanitized 500, not account absence. Responses contain only id/createdAtUtc and are no-store.
- One workspace per owner is enforced by a database UNIQUE index, not merely a prior lookup. Expected same-owner concurrent insertion recovers by rereading the winning row; PK/busy/other unique failures are not swallowed. No global memory lock is used. Creation is lazy through the explicitly approved GET, without arbitrary client mutation data. Register/login stay independent; this does not introduce workspace/content CRUD or weaken CSRF on existing unsafe auth actions.
- OwnerUserId is a logical reference without FK/navigation/cascade. Account deletion does not delete a workspace and can leave orphan records; account lifecycle/cleanup remain future work. Checking the account before access is not an atomic transaction with account deletion. Do not expose orphan records or use email as an ownership fallback. Future personal-workspace operations must derive owner from ICurrentUser and enforce ownership on the backend.
- Default session/cookie/CSRF/lockout/rate-limit protections remain unchanged. Restricted pre-controller exception handling includes the current-workspace path to sanitize native stamp-validation failures. Explicit new logs contain only a generic operation name; no owner, email, cookie, token, provider diagnostic, or raw exception is deliberately logged. Existing framework logging limitations still apply.
- Knowledge Maps stay global, anonymous demos without workspace ownership or new persistence. No frontend auth/workspace, sharing, roles, MFA, JWT, PostgreSQL, or additional dependency was introduced by the backend-only 3.3 slice. PersonalWorkspace has only Id, OwnerUserId, and CreatedAtUtc; no private learning content is added in this slice.

## Local Data Protection and HTTPS

The historical backend-only slices did not consume browser sessions; the current 3.4 client rules below apply in addition to their unchanged server protections.

Use ASP.NET Core Data Protection defaults for the current local single-instance host, without a custom key ring. On Windows with an available user profile, keys normally persist under `%LOCALAPPDATA%\ASP.NET\DataProtection-Keys` and are protected with DPAPI. This is host-dependent, not a deploy guarantee. Keep keys outside Git and logs; losing them can invalidate cookies/tokens. Future deployment must review persistent key storage, protection, and application isolation before relying on sessions.

Secure cookies remain required even in Development. Use the existing HTTPS API profile and trusted development certificate; do not weaken cookie attributes or TLS validation. A Vite HTTPS proxy target does not make the browser-to-Vite connection HTTPS. Local real-browser/session validation was completed in 3.5; in-process HTTPS-address tests alone do not verify actual TLS or browser SameSite enforcement. 3.2A does not install/trust certificates or modify the frontend.

## Phase 3.4 frontend session security

- Authentication remains browser-managed through __Host-Talynor.Auth, HttpOnly/Secure. There is no JWT, bearer/refresh token, JavaScript-created cookie, remember-me, or auth data in localStorage/sessionStorage/IndexedDB. User/workspace projections exist only in React memory; backend ownership remains authoritative.
- CSRF request tokens stay private to a per-hook client closure, in memory, never rendered/logged/persisted. Native fetch uses relative same-origin URLs, credentials same-origin, no-store and no automatic redirect following. Login/logout attach X-CSRF-TOKEN; me/workspace do not. Tokens are renewed before unsafe actions and after successful login, discarded on identity changes, and fetched for the anonymous identity when needed for next login. Login csrf_invalid gets one renewal without automatic password replay; logout permits at most one renewal/retry. This is not global token revocation.
- Password exists only as transient form/request memory, is cleared after attempts and unmount, and is never normalized, logged, persisted, sent in a URL, or placed in telemetry. Clearing React references is not secure erasure of managed memory. Email in the authenticated header comes only from me. Credential failure is generic; no lockout/account existence/counter is revealed.
- Bootstrap uses me then workspace. Protected-read 401 clears user/workspace and returns to login; network/500/invalid JSON does not imply an ended session. Post-login bootstrap failure shows an explicit session error/retry. Logout 204/401 clears local state and graph; operational failure preserves the shell with recoverable feedback. A network failure during POST can be ambiguous; retry/reload must rediscover the backend session rather than assume success or sign out automatically.
- Runtime validation rejects malformed user/CSRF/workspace responses. Public error rendering uses only known local messages/status categories, never raw ProblemDetails detail/title, submitted values, or server diagnostics. Operational/protocol map errors remain separate from session errors. Phase 4.3 rechecks the existing session flow on private-map 401; public demo endpoints remain available for backend regression.
- No cross-tab synchronization or polling is added. Each tab bootstraps from the backend; logout/expiry elsewhere is discovered on its next relevant protected request or reload. Conditional frontend UI is not an access-control guarantee.
- Vite requires an HTTPS API target with TLS verification and trusted external certificate/key files for browser HTTPS. The insecure anonymous-spike proxy flag is rejected. No certificate is generated/trusted by the application, no key is committed, and no Secure/SameSite/server setting is weakened. Local real-browser HTTPS/cookie/CSRF validation passed in 3.5; production hosting and full accessibility remain separately scoped work.

## Phase 3.5 validated security behavior and remaining limits

Local real-browser validation passed using trusted HTTPS on both browser-to-Vite and Vite-to-API connections. Assisted Chrome Storage inspection confirmed __Host-Talynor.Auth as HttpOnly, Secure, SameSite Lax, Path /, host-only, and a session cookie; normal login did not issue Identity.TwoFactorRememberMe. Assisted Network inspection confirmed same-origin /api requests, CSRF headers on login/logout POSTs rather than GETs, no Authorization Bearer or password query parameter, and no-store me/workspace responses with only their approved fields. Legitimate login/logout and missing/invalid-CSRF rejection passed. Cookie authentication stays browser-managed without JavaScript access; no JWT or auth data in localStorage/sessionStorage is introduced. Generic invalid-credentials feedback, password cleanup, refresh, local logout, and delayed cross-tab awareness were validated.

These results close Phase 3 only. Email confirmation and password reset remain absent; logout is local with no global revocation/session table; cross-tab awareness is not instant; login rate limiting remains process-local. SQLite-specific constraint classification still needs review during an explicitly authorized provider transition, and account/workspace deletion and orphan cleanup remain incomplete. At Phase 3 closure Knowledge Maps were only global, anonymous, in-memory demos; private persistence is added separately in 4.1 below. Automated tests cover lockout/rate limiting, stamp rejection and ticket deadlines, ownership, and workspace concurrency; local browser checks do not establish public-deployment readiness, exhaustive cross-site protections, real-device touch, full accessibility, or Kestrel body-limit enforcement.

## Phase 4.1 private knowledge graph security

- `GET /api/maps/{mapId:guid}` requires Authorize and derives workspace through ICurrentUser, current account validation and the existing personal-workspace resolver. No client WorkspaceId/owner selection exists; query parameters cannot override it. Reader queries require both map ID and server-resolved workspace ID. Nodes/edges belong to that scoped map and ChildMapId stays within its workspace.
- Missing and foreign maps have the same no-store 404 body, never 403/existence disclosure. Anonymous/invalid/removed accounts return sanitized 401 and invalid accounts cause local sign-out. Reader/provider and pre-controller native stamp errors become no-store 500 unexpected_error, without SQL, SQLite diagnostics, stack, private content or internal workspace ID. Added logs contain only a generic operation name; existing framework diagnostics/redaction limitations remain.
- Explicit FKs and composite map/node endpoint keys enforce referential and same-map edge integrity. SQLite migration-owned triggers reject cross-workspace child insertion/update and map moves atomically, including direct SQL writes; they do not rely on a client or an application precheck. Future schema rebuilds/provider transitions must preserve these protections. Positions must be finite; Domain validates required IDs/titles and bounded text. No rich content, files or rendering policy is introduced yet.
- Workspace/map and incoming child links restrict deletion; map deletion cascades its nodes/edges and endpoint deletion requires explicit edge removal. 4.2 adds authenticated, scoped delete/write APIs below; 4.1 introduced none. Account deletion still does not cascade to workspace/graph and orphan cleanup is unresolved; the account check is not atomic with deletion. Read snapshots/concurrent read tests do not solve future authoring concurrency.
- Responses contain no WorkspaceId/OwnerUserId, Identity data, XYFlow types or mock study metrics. Persisted maps are private, with no public/share endpoint. `/api/knowledge-maps/software` and `/csharp` remain anonymous demonstration data, separate from private persistence; the frontend used only demos through Phase 3; Phase 4.3 consumes the separate private source. No startup seed, provider/package change, global auth policy, CSRF weakening or production-readiness claim is added.

## Input and content validation

- Validate external input at application boundaries and enforce domain invariants on the backend.
- Define accepted values, sizes, and formats when the corresponding feature is designed.
- Treat links, notes, uploaded files, and other user content as untrusted. Review safe rendering and file handling before enabling the relevant content types.

## Dependency hygiene

- Add frameworks and dependencies only with a documented need and review of their maintenance and security implications.
- Keep the dependency footprint proportionate to the feature.
- Review supported versions and vulnerabilities as part of ongoing maintenance and production readiness.

## Secure logging

- Use structured logging with deliberate choices about recorded fields.
- Do not log secrets, authentication tokens, sensitive personal information, private learning content, or unrestricted request bodies.
- Ensure diagnostics and error responses do not expose sensitive configuration or internal details.

## Database and migrations

- The configurable SQLite file and its journal/WAL/SHM files are local sensitive data, never source artifacts. The Development default uses `talynor.local.sqlite` under the API content root, covered by the existing ignore rules. No credential is included in this connection string.
- Apply Identity, personal-workspace and knowledge-graph migrations explicitly; build and application startup must not create/migrate the database or seed accounts/maps. Persistence tests use disposable SQLite databases and remove their files. Do not log user secrets or sensitive data.
- Review migrations and their data implications before execution.
- Apply migrations only to the intended environment with explicit, controlled procedures.
- Make database provider changes explicit and validate the resulting behavior.
- Define backup and recovery procedures before production data is placed at risk; do not assume a destructive change is safe.

## Least privilege

- Give application identities, database access, and operational tools only the permissions they need.
- Keep development access and production access distinct.
- Avoid unnecessary public exposure of services or stored content.

Concrete controls, operational procedures, and security tooling must be designed in their relevant phases. This document does not authorize infrastructure setup during foundation.

## Phase 4.2 authoring security

All eight nested authoring endpoints require the validated cookie session and native CSRF. Current account/workspace is resolved server-side; store queries scope map and node/edge IDs together. No client owner/workspace choice, public authoring or global node/edge write exists. Unknown request properties are rejected. Missing/foreign target resources have identical 404; invalid foreign/missing child or edge endpoints have uniform 400 relation codes without owner/existence disclosure.

Application validates relations before save; existing composite FKs and SQLite triggers remain defense-in-depth. Referenced map/node deletion returns controlled 409 map_in_use/node_in_use, without silent edge deletion. Expected FK/known-trigger failures are translated only after confirming the corresponding condition; busy, PK, unknown constraints/outages remain sanitized 500. Explicit logs contain only generic operation names. Framework diagnostic/redaction limitations remain as before.

Writes use own DTOs/projections, no ownership fields in responses, and no-store on successful/error responses including pre-controller native stamp failures. The endpoint-only native 32 KiB request limit fits bounded escaped JSON; TestServer does not establish real-server enforcement. No new authoring limiter, cookie/CSRF policy change, concurrency tokens or provider/schema/dependency change exists. Account deletion/orphan lifecycle and non-atomic account check remain unresolved. Phase 4.2 left demos anonymous/transitional and frontend unchanged; current private frontend integration is described below. No deployment-security claim is made.

## Phase 4.3A discovery security

GET /api/maps is private and authenticated. ListKnowledgeMapsForCurrentWorkspace reuses the existing ICurrentUser/current-account/personal-workspace chain; the reader filters the server-derived workspace in SQL and projects only map ID/title. Arbitrary query parameters cannot select WorkspaceId or OwnerUserId. Foreign-workspace maps and in-memory demos never enter this collection, and no owner/workspace ID, graph content, position, child link or unnecessary timestamp is returned.

Success and error responses are no-store. An empty maps array is 200 and describes only the current workspace, providing no evidence about another workspace. Invalid/removed accounts use the existing sanitized 401/local-sign-out behavior; operational/provider and pre-controller stamp failures remain sanitized 500 rather than empty results. GET introduces no CSRF token requirement and leaves authoring/session protections unchanged.

Discovery creates/selects no map, defines no root/default and adds no public listing, frontend, seed, schema or dependency. It is currently unpaginated without search/filter/sort inputs; scale and future pagination/search require separate review. Phase 4.3 frontend integration is described below, without a production-readiness claim.

## Phase 4.3 persisted frontend security

The following records the historical read-only Phase 4.3 delivery. Current frontend authoring and CSRF-protected writes are documented in Phase 4.4 above.

Discovery and individual persisted reads are authenticated server-side. The frontend never sends a workspace/owner choice; an arbitrary URL map GUID is not a secret or an authorization grant. Missing/foreign maps remain indistinguishable 404 and the original URL remains until user navigation. The authenticated experience has no silent demo fallback.

Native GETs use relative /api URLs, credentials same-origin, no-store, redirects rejected and cancellation, without a CSRF bootstrap/header or Bearer token. Existing login/logout cookie and CSRF behavior is preserved. No auth data, map response, or local position is placed in localStorage/sessionStorage. History contains only navigation markers; the URL contains the requested map GUID, never credentials.

Runtime validation rejects invalid map payloads before visualization; React renders titles/descriptions as text. Safe local messages separate map protocol/network/500 errors from session errors and preserve the shell. A private-read 401 rechecks me/workspace once per failed read; if the session is still valid, retry is explicit, avoiding an automatic loop. Logout/account change unmounts the graph and cancels stale requests. AbortController, cleanup and request identity prevent obsolete responses replacing a newer visit. No frontend authoring request is introduced; drag is temporary visual state only.
